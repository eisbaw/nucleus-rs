## Hypothesis to test (falsifiable)

The cycle-163 `apply_host_data_relay_inject` pass is backend-agnostic at the ACFG layer; the driver wires it for mp-tcp-event only. The pass's pair-matching (Push and Wait siblings in the same Sequence, both non-host) and per-pair host-routing should compose cleanly across multiple pairs in the same Repeat body — and the pass has a regression test for the same-sequence multi-pair case (`multiple_pairs_same_sequence_each_rewritten_independently`).

But: 13's structure is qualitatively richer — 3-stage pipeline (conv_block_1 → conv_block_2 → classifier) means 2+ inter-stage transfer pairs per outer-batch iteration, with potentially different DataIds, tiles, and SeqTags. The pass should handle this naturally IF every pair is in the same Sequence. **Falsifier**: if any pair is split across nested Sequences / a Sequence boundary that the pass doesn't cross, the pair predicate doesn't fire and the TASK-0330 guard hits.

## Forward-carried lessons from cycle 163 (slice 2 / 09-arm)

These are the lessons the next implementer should INHERIT, not rediscover:

### L1 — Scope limit: pass operates on in-Repeat-body pairs ONLY

Cycle 163's first draft rewrote EVERY non-host-pair Push/Wait — top-level AND in-Repeat-body. The e2e gate caught a 05-stencil/distributed-2d × mp-tcp-event regression: top-level halo Push/Wait pairs (handled by cycle-149 flat host-relay via `relay_one` + tile-aware `render_wait_assign`) got an EXTRA host hop that broke tile-paste semantics. Host's local `img_in` is a fresh zero-init `Vec` that does NOT carry the source worker's slice; pushing 'the whole array' onward shipped zeros.

**Fix**: scope the pass to in-Repeat-body pairs only via an `inside_repeat` walker flag. Top-level pairs are LEFT ALONE; the cycle-149 flat host-relay handles them. This is the load-bearing correctness invariant of the pass.

**For 13-arm**: any extension MUST preserve this scope limit. A cross-sequence pair-matching extension (AC#2a) needs to still skip top-level (depth-0) pairs even if walking into nested Sequences.

### L2 — Existing walker machinery handles new host endpoints for free

The B2 choice was made over B1 (new `ACFGNode::Relay` variant) because the existing `backend-common/multi_worker_walker` machinery (`render_worker_events`, `collect_pre_init_sets`, `collect_worker_rendezvous`, `collect_pair_tiles`) ALREADY recurses into Loop bodies and ALREADY allocates per-worker locals + chan IDs for Wait/Push endpoints. Adding host as a Wait+Push endpoint via B2 produces correct host-side codegen WITHOUT touching the renderer.

This is load-bearing for 13: as long as the pass produces well-formed Xfer pairs (with hose seq → host wait, host push → dst wait), the renderer Just Works on host's per-iter Loop body.

### L3 — `pipeline_depth_for_seq` mirroring is mandatory

The pass mirrors any `pipeline_depth_for_seq` entry from the original seq onto both fresh seqs. Without this, mp-tcp-event's `Plan::build` chan_caps lookup ContractGaps on the fresh seqs because `build_sidecar` builds `transfer_buffer_for_seq` from `pipeline_depth_for_seq`. 09 has `buffer=4` on `transfer stream`; 13 likely has `buffer=3` (per the schedule's pipeline depth). Either way, the mirroring is mechanical and correct.

### L4 — Idempotence via the pair predicate

After one application, every fresh hop has host as an endpoint, failing the `src != host && dst != host` predicate. Second application is a structural no-op. Test: `apply_host_data_relay_inject_idempotent`. For 13: any extension must preserve this property.

### L5 — Match-exhaustiveness B1 vs B2 trade-off

If the AC#2 fix path requires changing the ACFG type (e.g. introducing a new variant after all), the cycle-163 B1 audit numbers apply: ~17 distinct `match` sites on `ACFGNode` repo-wide (`rg 'match.*node.*\{' nucleus-compiler/src/passes/`). B2 was picked precisely to avoid this. Strongly prefer additional B2-flavoured rewrites (more Xfer mutation) over B1-flavoured (variant introduction) unless the rewrite cannot be expressed structurally.

### L6 — `feedback-orchestrator-narrative-also-wrong` applies

Cycle 163's first draft followed the parent design narrative ('Option B interleaved per-Push host-relay') literally and rewrote top-level pairs too. The narrative was incomplete: the actual TASK-0330 surface is in-Repeat-body, not all non-host pairs. The e2e gate caught it. **For 13-arm**: don't trust the design narrative blindly — verify against the matrix at every cycle boundary.

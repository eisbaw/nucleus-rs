Codegen change in two backends + shared helpers in pthreads-sync exposed pub for mp-tcp reuse. Design choice A (per-loop AtomicU64 static + Drop guard struct) chosen over B (atexit/thread-local — not pure-std; bare-metal-hostile for tier-3 Renode) and C (Mutex<HashMap> registry — over-engineering). ## Design choice resolution (A vs B vs C)
A chosen: per-loop file-scope AtomicU64 + per-file Drop-guard struct. Std-idiomatic, no unsafe, lock-free fetch_add, predictable codegen, test-pinnable. B rejected: atexit + thread-local — atexit is libc-only (not in pure-Rust std), bare-metal-hostile for tier-3 Renode forward-carry. C rejected: Mutex<HashMap> global registry — over-engineering; each check loop has its own static at codegen time, so locking is dead weight.

## Honest limitations / gotchas
- No tier-1 e2e cell uses on_violation=log / =count today. The codegen-string tests + AC#3 cargo-build-and-run pair are the lower-bound coverage; the differential continues to compare only the 29 existing cells (none of which use check loop). Future cell with explicit Log/Count would close this gap.
- The sanitize_loop_var is defensive — current chumsky grammar (parser.rs) enforces loop_var must be a valid Rust ident at parse time, so the sanitizer is a no-op on every realistic input today. Documented in the helper comment.
- Multi-worker pthreads-sync still rejects check_frame with TASK-0052.05 ContractGap; mp-tcp-bufsync also rejects multi-worker check_frame on top of strip-mining (TASK-0181). On_violation handler choice in multi-worker context is filed as TASK-0052.05 future work (Count across processes is the harder design question — per-process counter vs aggregated).
- The Count Drop guard fires when fn main returns normally. On panic (e.g. in another part of the program) Rust still runs Drops via unwind, so the summary is robust. On std::process::exit() Drop is skipped (per std docs); not used in our generated code today, but a future codegen that calls exit() would lose the Count summary — fail-loud documentation worth carrying forward.
- The Count counter is process-local in mp-tcp-bufsync: each worker process gets its own NUC_CHECK_COUNT_<id> + its own Drop guard + its own summary line. For a multi-worker schedule both lines would appear on stderr (one per process). Aggregation is a TASK-0052.05 follow-up if/when multi-worker check_frame is enabled.

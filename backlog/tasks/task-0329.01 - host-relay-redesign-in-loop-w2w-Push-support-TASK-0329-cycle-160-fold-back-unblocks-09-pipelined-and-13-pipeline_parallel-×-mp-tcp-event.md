## Background

TASK-0329 cycle 160 lifted the CTRL-arm host-excluding-barrier rejection in mp-tcp-bufsync / mp-tcp-event via the new compiler-level pass apply_host_mediation_inject. With that lift, the two in-tree TASK-0329 trigger cells (09-producer-consumer/pipelined × mp-tcp-event, 13-cnn-inference/pipeline_parallel × mp-tcp-event) now advance past the host-excluding-barrier ContractGap into TASK-0330's defensive guard against in-loop worker-to-worker Push events.

Both cells have worker-to-worker Pushes nested inside Loop bodies:
- 09/pipelined: producer pushes \`stream\` per iteration of \`for n in 0..16\` to consumer
- 13/pipeline_parallel: inter-stage transfers fire per-iteration on the pipelined image-batch loop

cycle-149's flat host-relay (\`Plan::render_relay_phase\` emits one batch outside any loop) cannot drain these — over-count and mis-order failure modes are why TASK-0330's defensive guard rejects them.

## Acceptance criteria

### AC#1: substantive host-relay redesign

Choose and implement one of (or composition of):
- (A) **Threaded host-relay**: spawn a thread in host main that polls the reactor for inbound w2w frames and forwards them concurrently with host's own work. CTRL barrier still works (separate stream).
- (B) **Interleaved host-relay**: per-Push site emit. For each w2w Push event, host immediately runs \`relay_one(seq, dst_peer, cap)\` when its inbound[seq] arrives. Requires re-modeling host's event list to include relay events.
- (C) **Nested-loop relay splice**: detect schedule shape; if w2w Pushes occur inside a Loop, splice a per-iter relay block inside the corresponding host Loop body. Requires structural matching of the source Loop in host's event list (handled today by petri_to_events via Event::Loop preservation).

Coverage requirements: 09-producer-consumer/pipelined × mp-tcp-event AND 13-cnn-inference/pipeline_parallel × mp-tcp-event must emit + run + verify bit-identical against the pthreads-async oracle.

- Or is removed if the redesign covers every in-loop w2w Push shape (sibling guard in mp-tcp-bufsync handled symmetrically per paired-lift discipline).

### AC#3: e2e cell promotions

Both 09-producer-consumer/pipelined × mp-tcp-event and 13-cnn-inference/pipeline_parallel × mp-tcp-event promote from [[skip]] to [[required]], bit-identical against reference.bin.

## Cycle 161 (design-only) — design analysis

This cycle is a design-only orchestrator cycle (no code change). Anchors the architectural choices for the substantive host-relay redesign so the next implementation cycle has a precise starting point.

### State at cycle 160 (predecessor)

Cycle 160 landed the **CTRL-arm lift** as a compiler-level pass (`apply_host_mediation_inject` at `nucleus/nucleus-compiler/src/passes/host_mediation_inject.rs`). That pass mutates `Sync` participant sets only; it touches zero per-worker DATA-arm event lists. The DATA-arm gaps remain:

- **TASK-0330** defensive ContractGap (cycle 153, `nucleus/backends/mp-tcp-event/src/multi_worker.rs:1333-1346` and `nucleus/backends/mp-tcp-bufsync/src/lib.rs:1690-1704`): rejects any w2w `Push` found INSIDE an `Event::Loop` body. Blocks `09-producer-consumer/pipelined` and `13-cnn-inference/pipeline_parallel` on mp-tcp-event.
- **TASK-0332** defensive ContractGap (cycle 151, `nucleus/backends/mp-tcp-event/src/multi_worker.rs:1133-1200` and `nucleus/backends/mp-tcp-bufsync/src/lib.rs:1731-1783`): rejects worker event lists where a w2w `Wait` precedes any w2w `Push` at top level. Blocks `05-stencil/distributed-2d` on mp-tcp-event.

### Runtime constraint discovered cycle 161 (load-bearing)

`runtime_src.rs:617` documents: *"RefCell single-threaded — every worker process has exactly one thread in mp-tcp-event."* The `Reactor` (single source of mio Poll + sockets + inbound/outbound queues) lives in `Rc<RefCell<Reactor>>` and the `Chan<T>` borrows it mutably per-call. Adding a relay thread to host means EITHER moving the reactor behind `Arc<Mutex<>>` (RefCell -> Mutex is a wide signature change; locking semantics interact with the reactor's pump_once draining model), OR running the relay on a SEPARATE reactor that owns its own subset of sockets. The current "one reactor per worker" architectural contract is load-bearing for this decision.

### Failure-mode analysis of the three trigger cells

| cell | shape | deadlock mechanism |
|---|---|---|
| 05/distributed-2d × mp-tcp-event | top-level w2w pairs; **wait-before-push order** | workers do all halo `wait()`s before any halo `push()`. Host relay (in any sequential position) cannot make forward progress: every relay_one(seq) waits for the src worker's push, which the src worker hasn't reached yet because src is also waiting on its own halo-in. Cycle. |
| 09-producer-consumer/pipelined × mp-tcp-event | w2w push inside `for n in 0..16` Loop body | producer's iter-1 push back-pressures on its outbound queue with cap=1 because host's flat relay (outside the Loop) hasn't drained iter-0 yet. Deadlock at second iteration. |
| 13-cnn-inference/pipeline_parallel × mp-tcp-event | per-batch-iter w2w inter-stage transfers inside outer pipelined loop | same as 09 mechanically. |

### Four candidate fixes

#### (A) Threaded host-relay
- Spawn a dedicated relay thread in host's emitted `main()`.
- Either: (A1) reactor moves to `Arc<Mutex<Reactor>>` and the relay thread takes the mutex when it does pump_once OR (A2) split-socket model — host's DATA sockets transfer to a relay-thread-owned `RelayReactor`; main thread keeps CTRL (already separate from reactor) and any host-side data Push/Wait via a request-channel (only needed if host does direct DATA — examples 1-2 do, but the three trigger cells DON'T).
- Coverage: resolves all 3 cells.
- Estimated cost: 200-300 LoC across runtime_src.rs + multi_worker.rs (mp-tcp-event), plus paired-lift in mp-tcp-bufsync.
- Risk: real concurrency hazard. Mutex contention vs reactor's draining model. Thread-shutdown signal needs design.

#### (B) Interleaved per-Push relay
- Synthesize a "relay this seq now" event for host at each w2w Push site in the ACFG; project it via acfg_to_events into host's event list.
- Coverage: **resolves only 09 and 13 (in-loop case)**. Does NOT resolve 05/distributed-2d: even if host's relay events are interleaved with workers' events in lockstep, the wait-before-push cycle is sequential in nature — every host relay event waits on some worker's push, and ALL workers wait first. Cycle is unbreakable single-threaded.
- Estimated cost: 150-250 LoC (a new compiler pass `data_relay_inject` analogous to cycle-160's `host_mediation_inject`, plus host event list rendering for relay events).
- Risk: low concurrency risk; moderate ACFG-pass complexity.

#### (C) Nested-loop relay splice
- Detect Loop nesting in workers' events; splice a relay sub-block INSIDE host's mirror Loop body.
- Coverage: resolves only 09 and 13. Same wait-before-push cycle as (B) on 05.
- Estimated cost: 200-300 LoC (Loop-shape matcher in host's event list, relay-within-loop emitter).
- Risk: brittle to schedule-shape variations.

#### (D) Push-before-wait reordering at worker event lists + relay-before-bar_0
- Cycle-161 NEW finding. Reorder each worker's event list so all w2w Pushes precede all w2w Waits within a top-level boundary, IF dependency analysis shows the Push payload doesn't depend on any preceding Wait result. Also move host's relay block from "after bar_0" to "before bar_0" (or more generally, before the first wait-bearing Sync).
- Coverage: **resolves only 05/distributed-2d**. Does NOT resolve 09/13 — in-loop Push back-pressure is independent of order.
- Estimated cost: 50-100 LoC (analysis pass in `petri_to_events` or a new `event_reorder_safe_pushes_first` pass + splice point adjustment in `relay_phase_insertion_point`).
- Risk: dependency analysis must be conservative — reordering an unsafe Push (one whose payload was computed from a preceding Wait) corrupts the schedule.

### Composition

(A) alone resolves all 3 cells. (D) + (B) together also resolve all 3 cells. (D) alone resolves 05. (B) alone resolves 09 + 13.

### Honest scope realisation

The original TASK-0329.01 framing ("substantive host-relay redesign") combined the two failure modes. They are architecturally distinct:
- 05 needs concurrency (Option A) OR safe reordering (Option D). Cannot be fixed by event-list synthesis alone.
- 09/13 need event-list synthesis (Option B/C) OR concurrency (Option A). Cannot be fixed by reordering alone.

This warrants splitting the TASK-0329.01 keystone into two slices.

### Recommended next-implementation slice

Slice 1: **Option (D)** — push-before-wait reordering. Filed as TASK-0329.02 (see follow-up). Smallest blast radius, unblocks 05/distributed-2d × mp-tcp-event.

Slice 2: Option (B) interleaved per-Push relay via ACFG pass. To be filed separately after slice 1 lands and the ACFG pass infrastructure is exercised. Unblocks 09/pipelined and 13/pipeline_parallel × mp-tcp-event.

Slice 3 (deferred): Option (A) full threaded relay — only if (B)+(D) prove insufficient for some future schedule shape.

### What this cycle does NOT do

- No code change.
- No e2e cell promotion.
- The three trigger cells remain `[[skip]]` on mp-tcp-event.
- The TASK-0330 and TASK-0332 defensive guards stay in place; they continue to surface the gap fail-loud.

### Why the original TASK-0329.01 cost estimate looks understated

The cycle-160 follow-up filing for TASK-0329.01 estimated 240 LoC (per the reconnaissance pass). That was Option (A) framed as a single fix. After cycle-161 design analysis: 240 LoC was the threaded-relay estimate alone, and threaded relay is now slice-3-deferred. The two replacement slices total ~300-400 LoC across the codebase. The cost increases because doing (B) and (D) is two separate compiler-pass scaffolds (analogous to cycle 160's `host_mediation_inject`), but each one is structurally simpler in isolation than a unified threaded-relay redesign. Risk profile is lower (no concurrency).

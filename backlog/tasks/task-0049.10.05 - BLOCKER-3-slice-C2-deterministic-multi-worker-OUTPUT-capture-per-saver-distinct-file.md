Slice C2 of TASK-0049.10 (decomposed from slice C; BLOCKER 3 = multi-worker output capture ordering). DEPENDS ON C1 (TASK-0049.10.04) for the classification/sidecar threading.

GAP: ex14 has TWO savers — fe (fe_emit(spk_out[frame])) AND rf (rf_transmit(bt_out[frame])); both have saves_output=true so render_multimachine_resc (multimcu.rs:608-612) attaches 'usart1 CreateFileBackend $uartFile true' to BOTH machines => both stream to the SAME $uartFile, concatenating by non-deterministic Renode write order. reference.bin = spk_out[0..256] ++ bt_out[256..512] (reference generator main.rs:149-160; spk-first then bt_out — NOT the input's mic-first order). So the captured bytes must be fe's spk_out THEN rf's bt_out, deterministically.

MECHANISM (recommended — per-saver distinct capture, ordering pushed to slice D's recipe): give each saver its OWN capture file (e.g. $<worker>Uart, 'usart1 CreateFileBackend $<worker>Uart true') instead of one shared $uartFile. Slice D's recipe then concatenates the per-saver files in CANONICAL OUTPUT-LAYOUT order (output-symbol declaration/DataId order: spk_out declared before bt_out => spk_out first) and byte-exact-diffs vs reference.bin. ALTERNATIVE rejected unless needed: a single designated aggregator worker (route both spk_out+bt_out to one MCU's USART1) — costs extra cross-MCU transport (fe would have to link_push spk_out to rf), more complex, defer. Document the chosen mechanism + the output-layout-order coupling to the reference generator (same assumption class as C1's input order).

SCOPE: output capture wiring only. The actual ordered concat + ex14 byte-exact is slice D.

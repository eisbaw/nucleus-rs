## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Gating de-risk for parent TASK-0048 AC#1 (real STM32H7 NucleusShim with DMA controller). Before touching the WORKING byte-exact synchronous Usart1Shim (which reads a Renode-injected axiSram region and writes USART1 TDR in a CPU loop), prove EMPIRICALLY that Renode's bundled stm32h743 model can drive a USART1 TX via the DMA engine (MemoryToPeripheral), not just a CPU store loop. Static source read (this cycle): Renode STM32DMA.HandleEnable fires MemoryToPeripheral transfers IMMEDIATELY on the EN bit (no peripheral DMA-request wire / DMAMUX routing needed for TX — that path is PeripheralToMemory only); DmaEngine.IssueCopy 'write to peripheral' branch with PINC=0 writes every byte to the fixed TDR address via sysbus.WriteByte, each dispatching to STM32F7_USART HandleTransmitData->TransmitCharacter (emit). So real-DMA TX SHOULD work. Per CLAUDE.md recurring lesson #5 (cheap empirical verification beats trusting the narrative), confirm with a minimal DMA-TX smoke firmware before declaring GO and before scoping the real shim. Anchors: tests/renode/uart-smoke/ (polled-TX template to mirror), platforms/cpus/stm32h743.repl (dma1/dma2 @0x40020000/0x40020400 STM32DMA, dmamux1 @0x40020800), backends/embedded-pattern/src/skeleton.rs (Usart1Shim::dma_push current synchronous body). This spike does NOT modify the production shim; it only adds a hand-written DMA smoke harness + records the GO/NO-GO + M10 definition-of-done decision (is the synchronous injected-region shim a sufficient M10 state, given real-async-DMA's marginal value is unverifiable on a non-cycle-accurate emulator?).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
=== Empirical de-risk result: GO (real-DMA USART1 TX IS modellable in Renode) ===

STATIC SOURCE READ (Renode 1.16.1 bundled C# models, store path under
lib/renode/src/Infrastructure/.../Peripherals/):
- DMA/STM32DMA.cs HandleEnable (lines ~237-245): for direction != PeripheralToMemory
  (i.e. MemoryToPeripheral or MemoryToMemory) the transfer fires IMMEDIATELY on the
  SxCR EN-bit write — NO peripheral DMA-request wire and NO DMAMUX routing needed. The
  request-driven OnGPIO path is PeripheralToMemory ONLY. => the absence of a
  `usart1 -> dmamux1` DMA-TX request line in platforms/cpus/stm32h743.repl (cf. spi4's
  explicit `DMARecieve -> dmamux1@83`) is IRRELEVANT for TX.
- Main/.../DMA/DmaEngine.cs IssueCopy destination branch (lines ~156-187, "Write to
  peripheral"): destination is the USART (not MappedMemory) => per-unit loop; with
  PINC=0 (IncrementWriteAddress=false) `offset` never advances, so EVERY byte is written
  to the FIXED TDR address via sysbus.WriteByte. Source M0AR in RAM with MINC=1 reads the
  whole buffer.
- UART/STM32F7_USART.cs: TDR write (reg @0x28) -> HandleTransmitData -> base.TransmitCharacter
  (emit), gated by transmitEnabled && enabled (so CR1=UE|TE is load-bearing). CR3 DMAT
  (bit 7) is a no-op flag in the model (no callback) — set anyway for HW faithfulness.

EMPIRICAL PROOF (the project's recurring lesson #5: verify, don't trust the narrative):
- Added tests/renode/dma-uart-smoke/ (hand-written STM32H743 no_std bin: configures DMA1
  stream0 PAR=USART1.TDR, M0AR=&RAM buf, NDTR=len, DIR=MemToPeriph|MINC, then EN; NO CPU
  store to TDR / no TXE poll) + `just renode-dma-uart-smoke`.
- Captured `NUC-DMA-OK` (full 11-byte payload incl. \n) byte-exact, DETERMINISTIC x3.
  Because the firmware has zero other TDR-write path, every captured byte reached USART1
  via the DMA engine writing the fixed TDR. The multi-char payload proves the
  non-incrementing-destination write loop (all bytes to TDR, not just the first).
- NEGATIVE CONTROL: neutering only the EN-set write -> EMPTY capture, recipe FAILs loud
  (exit 1). Confirms causality: the DMA EN trigger is the sole cause of the emission; the
  assertion bites.

GATE (this cycle, additive harness only — zero nucleus-crate change; dma-uart-smoke is its
own [workspace], NOT in `just ci`/e2e-matrix): justfile parses; build+clippy cache-clean;
just test + test-release exit 0; just e2e 301/246/0/55/0 (baseline, required-fail 0).

M10 DEFINITION-OF-DONE DECISION (parent TASK-0048 AC#1):
The synchronous Usart1Shim (reads a Renode-injected axiSram region, CPU-writes TDR) is the
CURRENT working byte-exact shim. This spike proves a real-DMA dma_push is ALSO modellable.
But on a non-cycle-accurate emulator the DMA path produces the SAME captured bytes with NO
additional verifiable fidelity (Renode fires the transfer synchronously on EN — there is no
real async overlap / completion-IRQ timing to validate; cf. the already-documented
TXE-hardwired-true back-pressure gap). So real-DMA is a hardware-faithfulness upgrade whose
marginal value is UNVERIFIABLE here. RECOMMENDATION: real-async-DMA shim is GO-feasible and
worth doing for HW faithfulness, but is NOT required for an honest M10 DoD; if pursued, the
output buffer must move to a DMA-accessible region (axiSram/SRAM, NOT DTCM — DTCM is not
DMA-reachable on real H7 silicon; Renode papers over this, see memory.x note). Follow-up task
to be filed with these findings forward-carried.

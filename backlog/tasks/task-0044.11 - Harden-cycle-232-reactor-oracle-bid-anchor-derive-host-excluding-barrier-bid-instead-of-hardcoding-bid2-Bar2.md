## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Cycle-232 architect review P3-1 on TASK-0044.08. The two cycle-232 reactor tests (transpose_15_distributed_rows_event_host_excluding_barrier_mediated, transpose_15_distributed_rows_uds_equiv_tcp) hardcode the post-mediation anchor as struct Bar2 / let bar_2 / barrier_cross(..., 2) — i.e. they assume the host-excluding barrier is SyncTag(2)/bid=2.

The implementer disclosed this coupling but mischaracterized it as 'fails loud on a sync-tag renumber'. The architect verified it actually fails SILENT-PASS in one direction: all 3 host-INCLUDED barriers in 15-transpose/distributed-rows span all four compute workers {host,w0,w1,w2,w3}, so if a future sync-tag renumber moved the host-excluding barrier off bid=2 and a host-included barrier took bid=2, host would already carry a Bar2 shim + barrier_cross over w0..w3 at bid=2 post-mediation -> the post-mediation assertion passes WITHOUT the mediated host-excluding barrier being present. (This is a feedback-implementer-disclosure-mechanism-wrong instance: honest disclosure, wrong mechanism.)

NOT a current defect: the PRE-mediation half (Err(ContractGap), participant-set = WorkerId(1..4), bid-agnostic) carries the real load-bearing bite and stays robust, so the tests are over-specific, not broken. The cycle-231 openmp-rs/poll siblings already use participant-set anchors (Barrier::new(4) / {w0,w1,w2,w3}) which are robust.

Scope: in the two cycle-232 tests, derive the host-excluding barrier's bid from the unmediated barrier_participants (the tag whose participant set lacks the host) and interpolate it into the post-mediation anchor, instead of hardcoding 2. Then the post-mediation half also fails loud under a renumber.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
=== Cycle-255 SPIKE RESULT (provisional, pre-review) ===
Question: on early-exit at k<N, does the 16-jacobi final gather read generation-k or generation-N? ANSWER: generation-N (WRONG/stale-zero).

EMPIRICAL (cruft/spike-0341-02-01-01/jacobi_earlyexit_spike.rs, replicates the EXACT generated index arithmetic, verified against the shipped pthreads-sync src/main.rs): with H=W=8, ITERS=4, early-break after generation k=2:
  - codegen reads field[ITERS=4] = ALL-ZERO (slice 4 never written on early-exit)
  - correct generation-2 read = nonzero ([39,61,69,74] at interior row 1)
  - they DIFFER -> the fixed-iteration final-read is structurally wrong under early-exit.

ARCHITECT ASSUMPTION CORRECTED: field is NOT a 2-slice k%2 double-buffer. It is a FULL history array i32[ITERS+1][H][W] (generated: vec![0; (ITERS+1)*H*W], generation t at slice stride H*W). The prev-gen index (t+ITERS)%(ITERS+1) is only used as the READ index inside the step; each generation WRITES its own slice field[t]. The final extraction (prog.algo.nuc:161, generated main.rs:22) reads the HARD-CODED constant slice field[ITERS].

DESIGN CONSEQUENCE (forward-carried to S4/S5): the convergence variant must read the RUNTIME-current generation slice field[k] where k = the break generation (the loop var t at break), NOT the compile-time field[ITERS]. Because the encoding is full-history, generation-k IS available and correct (slices 0..k all valid; only k+1..N are unwritten) — no double-buffer aliasing. So the fix is purely: make the final-extraction slice index runtime (the captured break-generation), and the lowering must thread that value to the extraction loop.
SCALING NOTE: full-history buffer is (N+1)*H*W; a large convergence cap N makes it large. A 2-slice double-buffer is the natural OPTIMIZATION (not required for correctness) — file as an S4/S5 follow-up if N is large.
VERDICT: GO for the epic — the question is answered and the issue is concrete + fixable in S4/S5.

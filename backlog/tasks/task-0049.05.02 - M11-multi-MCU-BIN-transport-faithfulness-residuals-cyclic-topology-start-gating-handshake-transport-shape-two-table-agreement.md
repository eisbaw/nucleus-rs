## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Deferred scope from TASK-0049.05 (the structural+02-split-add slice landed value-correct). Two residual faithfulness items for richer interconnects: (1) BOOT-ORDER for non-DAG topologies — multimcu::compute_boot_order is a receivers-first HEURISTIC (waits_before_first_push) correct only for pipeline DAGs; a cyclic interconnect (mutual early sends) has no static receivers-first order and needs a real RX-ready handshake in the firmware + .resc (documented limit at multimcu.rs ~:399-404). (2) TRANSPORT-SHAPE two-table agreement ACROSS THE WIRE (forward-carried from TASK-0049.07/0363): the sender link_push len (size_of_val of its local) and the receiver link_recv len (size_of_val of ITS local) must match, and that is only checked per-worker at codegen, never at contract/link level across the pair. Add a cross-pair shape-agreement check (or at least an emit-time fail-loud) so a sender/receiver array-size mismatch cannot silently deadlock/truncate over the UART link. Both are inert for 02-split-add (single peer, equal [i32;256] arrays).

## Implementation Notes

CONCRETE EX14 REPRO + SCOPE WIDENING (from TASK-0049.10.08 slice-D end-to-end run, 2026-06-04): running the GENERATED ex14 multimcu (just renode-multimcu 14-hearing-aid embedded_multimcu_sync) DEADLOCKS rf at frame 3/4: fe captures 256B (4 frames), rf captures 192B (3 frames), combined 448 != 512. Proven a true deadlock not a slow run (rf pinned at 192B after 5+ min wall-clock / RunFor patched to 8.0s).

The deadlock is BROADER than this task currently scopes ("size mismatch", item 2). All ex14 link arrays are [i32;64]=256B so sizes AGREE; the actual defects are: (a) MULTIPLE distinct transport seqs share ONE byte-FIFO USART with NO per-seq framing/demux — e.g. dsp<->fe hub (usart2) carries seq0+seq2 (fe->dsp) and seq4 (dsp->fe); dsp<->rf hub carries seq1+seq3 bidirectionally. link_recv(seq,...) reads the next N raw bytes regardless of seq. (b) PUSH/RECV ORDER divergence across the pair: fe pushes seq2 THEN seq0 each frame, dsp recvs seq0 THEN seq2 -> the two streams cross, framing drifts each frame, rf starves at frame 3. Need EITHER a per-seq frame tag/demux on the shared hub, OR a distinct hub per seq, OR a codegen guarantee that push order == matched recv order per pair. Add this to this task's scope (or file a dedicated child) — it is the precise blocker for ex14 value-correctness (TASK-0049.10 / 0049.02), gating slice-D AC#4 (TASK-0049.10.08).

Also: render_multimachine_resc comment multimcu.rs:1216-1217 ("RunFor 0.3 runs the whole co-simulation to completion, bounded fully determinate") is a doc-lie beyond the 02-split-add single-pass case; even after the transport fix, a 4-frame x 3-MCU pipeline needs a larger or saved-byte-count-gated run window.

REVIEW-CARRIED from TASK-0049.10.08 slice-D gate (architect P3-2): add an EMIT-TIME fail-loud guard (or explicit // LIMIT) in map_seqs/mmcu_link_base (multimcu.rs ~318-339) for the case where >1 transport seq collapses onto the SAME UsartSlot in a given direction — today that unframed shared-FIFO multiplex is caught ONLY by the downstream tier-3 byte-count gate (not in just ci), so it ships as a latent Renode-runtime deadlock. This REFUTES the prior durable assumption "one hub per worker-PAIR is sound because opposite directions do not temporally overlap on a DAG" — it does NOT cover SAME-direction multi-seq on one shared byte FIFO. Three candidate fixes (pick in this task): (a) per-seq frame tag/length header on the wire; (b) a DISTINCT hub/USART per seq (not per peer-pair); (c) a codegen guarantee that push order == recv order per shared USART.

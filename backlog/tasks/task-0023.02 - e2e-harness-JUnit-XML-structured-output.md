**Honest limits (read these before signing off):**

- `--output PATH` deferred (Stage 1 stdout-only, as the task hint allows). CI runners can shell-redirect; revisit if a downstream consumer can't accept stdout.
- Under `NUC_NONDET_TEST=1` or `NUC_XBACKEND_NEGATIVE=1`, the harness still emits the `NUC_*_CELLS=<n>` machine-checkable signal lines on stdout — these are NOT XML and would corrupt a stdout-captured XML document. NOT a regression (those env gates are used by `determinism-check-negative` / `xbackend-check-negative` recipes which run with the default text format), but if a future CI matrix combines `--format=junit` with those env gates, it must redirect the signal lines first. Documented at the call site (the existing `// Both emitted on STDOUT … gate-only` comment block already covers this).
- XML escaping covers `<>&"'` and `]]>`-in-CDATA. ASCII-control bytes (`\x00..\x1f` except whitespace) inside cell names or detail strings would still produce technically-invalid XML 1.0 — but the manifest constrains all three cell ID fields to ASCII identifiers today, and the detail strings come from internal `format!`/`Display` impls that never produce control bytes. NOT defending against arbitrary attacker-controlled bytes (the harness reads only the trusted `e2e-matrix.toml`).
- Exit-code semantics, all `NUC_*` env gates, and the parallel-execution path are unchanged across format choices: only the rendering function differs.

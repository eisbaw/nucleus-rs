## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Second sub-slice of TASK-0438. Make the embedded-pattern backend emit a STRUCTURALLY DISTINGUISHABLE code path for a DMA-async transport edge vs a PIO-sync one, driven by the `TransferPolicy.transport` field threaded in TASK-0438.01.

Sites (from parent pre-brief): nucleus/backends/embedded-pattern/src/render.rs:348-391 (link_push/link_recv lowering) + skeleton/multimcu.rs:238-258 (concrete UART byte loop) + multimcu.rs:202-335 TransportPlan::build. The TransportPlan/per-channel context must learn the mode so render diverges.

DMA-async path: emit a descriptor-arm + IRQ-wait stub (poll DMA-complete flag, or wfi-loop — decide Q#4 here; spin is acceptable for byte-exact differential, document the choice). The byte movement may still ride the SAME USART fabric (reuse UARTHub) — the point is the EMITTED Rust structurally differs (DMA arm + completion wait), not that a real silicon DMA engine runs.
PIO-sync path: keep the existing volatile byte-by-byte loop (skeleton/multimcu.rs usart_putc/usart_getc).

HONEST CONSTRAINT: if the DMA path needs a real Renode DMA engine to remain byte-exact, that is high-risk (cf. deferred TASK-0048.12). Prefer a DMA-SHAPED emit that is still correct over the existing transport (the M10-precedent honest-sync-shim approach). Document precisely what is modelled vs real.

Must keep 02-split-add + 14-hearing-aid (no mode= -> default Pio) BYTE-EXACT.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
forward-carried from TASK-0438.01 (architect review P3.3): `sync, mode=dma` and `async, mode=pio` cross-combinations currently parse and resolve WITHOUT rejection — transport mechanism (pio/dma) is treated as orthogonal to the sync/async dataflow semantic. This is defensible (a DMA engine can do a caller-blocking transfer) but was NOT an explicit decision. When you implement divergent codegen, EXPLICITLY decide whether any (sync|async)x(pio|dma) combination is invalid and should be a typed capability/lower error, rather than silently inheriting acceptance. If all 4 combos are valid, document why; if not, add the guard + negative test.
Also forward-carried: TransferPolicy.transport is the field to branch on (passes/transfer_inject/ordering.rs policy_from_directive). The serde-on-AST-enum layering departure for TransportMode is documented in sched/ast.rs — if you prefer the NotifyKind->NotifyMode mirror pattern, the conversion point is trivial.

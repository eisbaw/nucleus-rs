## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Architect P3.1 (cycle-243, TASK-0422 review). The inv(2) production gate is wired at driver/src/main.rs:785 (validate_event_lists(&per_worker) before dispatch_backend). The cycle proves: (a) the validator LOGIC rejects unmatched pairs (unit bite test task0422_gate_wired_reject.rs), and (b) it does not reject any valid corpus program (e2e 385/328 green). But NO test exercises cmd_build's actual CALL of the validator. Because no valid .nuc source produces an inv(2) violation, the reject arm of the driver path is undriveable from real input — so if a future refactor deleted line 785, every unit test would still pass AND e2e would stay green (e2e is positive-direction only: it proves the gate does not reject valid input, never that the gate is still present/invoked). This is a latent silent-removal risk for a fail-loud tripwire. SCOPE: add a cmd_build-level (or near-driver) test that injects an inv(2)-violating EventList via a test seam and asserts the driver path returns the validation Err. The seam does not exist today; designing the least-invasive one (e.g. a #[cfg(test)] hook, or factoring the post-projection gate sequence into a testable fn taking per_worker) is the task. Keep it honest: do NOT fake an end-to-end .nuc reject (none exists). LOW priority — the structural argument + e2e green make the gate correct TODAY; this guards against future regression. Pointer: driver/src/main.rs cmd_build ~736-793; nucleus-compiler/src/event_validate.rs validate_event_lists.

Implementation Plan (cycle-245):

SEAM CHOICE: PRIMARY (factor the post-projection gate). Extract the accumulator cross-check + validate_event_lists gate (main.rs ~737-791) into a named fn `gate_per_worker_for_dispatch` placed in a NEW driver sub-module `driver/src/gate.rs` (mirrors the existing dispatch.rs/args.rs carve-out pattern, TASK-0388). main.rs `cmd_build` then calls `gate::gate_per_worker_for_dispatch(&linked.algo, &per_worker, &sidecar, &names.data)?`.

WHY sub-module not inline mod in main.rs: driver is a BIN crate (no lib target), so driver/tests/*.rs integration tests cannot see driver internals (only the existing task0371-style subprocess tests work for bin crates). The only way to unit-test the extracted fn is a `#[cfg(test)] mod tests` compiled INTO the bin crate. main.rs is already 865 LoC; an inline test mod risks crossing the 1000-LoC mega-file fence. A separate gate.rs keeps main.rs small and houses the fn + its inline test cleanly.

BEHAVIOR-PRESERVING: same order (accumulator THEN validate), same EXACT error strings, same `?` propagation. MOVE the big explanatory comments (745-784 + 704-736) into gate.rs docstring/inline (no stale comment left at old site). e2e MUST hold 385/328/0/57/0 exactly.

(2) accept — matched pair returns Ok (non-tautology guard).

HONEST RESIDUAL: this proves the EXTRACTED gate fn rejects + makes the cmd_build call a single visible line; it does NOT prove the literal call line executes (a refactor could still delete that one line). Documented in docstring + final summary. NOT adding a production-path fault-injection hook (maintainability smell this project disfavors).

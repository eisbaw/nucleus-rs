## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Architect P1 on TASK-0049.05 (commit e8ae76d). The multi-MCU BIN MultiMcuShim lowers EVERY Event::Sync to a no-op irq_barrier (render.rs ~:369). This is value-correct ONLY when the barrier ordering is already subsumed by a blocking Push/Wait data edge — true and VERIFIED for 02-split-add (its tag0/1/2 Syncs are control-only but data-edge-redundant; byte-exact diff holds). But the no-op is UNCONDITIONAL: a schedule whose correctness needs a standalone control barrier with NO co-located data edge would be SILENTLY miscompiled. The compiler can distinguish the two cases (happens-before subsumption analysis). Add a typed EmitError on the multi-MCU BIN path that REJECTS a control-only Sync whose ordering is not provably carried by data edges (matching the repo fail-loud-tripwire discipline; cf. TransferInjectError::CumulativeWholeArrayFallback precedent). NB a naive "reject any Sync" is WRONG — it would reject the value-correct 02-split-add; the guard must detect non-redundant barriers. Mitigation today: the tier-3 acceptance is always the byte-exact reference.bin diff, which fails loud if the no-op breaks a schedule — so the risk is bounded to trusting BIN output without that diff.

## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-0023 ships sequential cell execution. cargo build saturates cores for one cell at a time; running cells in parallel mostly contends for the build cache. As the matrix grows past pthreads-sync (M3+), evaluate spawning N=ncores worker tasks with separate target dirs per cell.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Implementation plan (cycle-51):

1. Add `--jobs N` / `-j N` flag to `parse_args`; default 1 (preserves byte-for-byte sequential behaviour, gate untouched when flag absent).
2. Validate N >= 1; cap at a sane upper bound (e.g. 64) to avoid pathological fork bombs.
3. Refactor the two cell-loops in `run_inner` (run-mode at ~L2510 and determinism-mode at ~L2383) to dispatch via a small helper `execute_cells_parallel(jobs, planned, run_fn)` that:
   - if jobs==1: same path as today (sequential loop, in-order progress lines).
   - if jobs>1: spawns `min(jobs, planned.len())` worker threads via std::thread + std::sync::mpsc + an `Arc<Mutex<VecDeque<idx>>>` work-queue. Workers pull next index, run the cell, push (idx, result) over the mpsc.
4. Buffer per-cell progress lines so completion-ordered emission stays parseable; format `[i/N]` lines as today but emit them at completion time (so output is not interleaved mid-cell).
5. Collect results in original `planned` order (re-sort by idx at end) — the summary tables, gate signals (`NUC_NONDET_PERTURBED_CELLS=`, `NUC_XBACKEND_CORRUPTED_APPLIED/_DETECTED=`), and exit-code logic are all order-insensitive (they iterate `results`), but stable order keeps the summary table deterministic.
6. Update `print_help` to document `--jobs N` / `-j N`.
7. Add a unit test for the arg parser (`--jobs 4`, `-j 4`, bad value → error).

Why std::thread + mpsc and not rayon: harness has zero deps on rayon today; cell count is small (<=88); contention is on subprocess spawn, not on Rust-level work; std lib is sufficient and keeps the dependency footprint minimal (MPED principle: smallest dep that fits).

Send/Sync concerns:
- Paths is composed of String + PathBuf, trivially Send+Sync — pass as Arc<Paths>.
- PlannedCell / CellResult / DetCellResult contain only owned data; trivially Send.
- run_cell / check_cell_determinism each spawn their own cargo subprocesses; the per-cell scratch is unique by construction (TASK-0182's run-id segment). No shared mutable state.
- The two negative-gate env reads (NUC_NONDET_TEST, NUC_XBACKEND_NEGATIVE) are per-cell std::env::var reads against a constant env — re-entrant safe.
- Cargo's per-workspace lock on the nucleus driver target dir will SERIALISE the brief `cargo run --bin nucleus` lock-acquire phase but not the work; per-cell `cargo build` runs in disjoint scratch trees with their own target dirs.

Risks / honest limits:
- Memory: each concurrent `cargo build --release` of an emitted project costs ~200-500MB peak. With --jobs 4 on a 14-core 30GB host: comfortable. Higher --jobs values risk OOM on smaller hosts; help text will note this.
- Output ordering: per-cell progress lines emit in completion order, not planned order. Summary table re-sorts.
- The two negative recipes (`determinism-check-negative`, `xbackend-check-negative`) currently invoke the harness sequentially. Adding `--jobs N` is opt-in — those recipes keep their current sequential invocation, so their per-cell discipline is unchanged.

Verification:
- Pre-fix wall-clock baseline (sequential `just e2e`).
- Post-fix gates: `just e2e` (sequential — must stay 88/70/0/18), `--jobs 4` (same tally, faster), determinism-check-negative, xbackend-check-negative, just test, just clippy.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Forward-carried from TASK-0182 (Done, commit 5735b19): the shared-tree CWD race that blocked safe concurrent harness runs is FIXED via a process-wide run-id path segment (nucleus/target/e2e-matrix/<run-id>/<cell>, e2e-determinism/<run-id>/<cell>__<label>), computed once in Paths::discover. This is a PREREQUISITE for parallel-cell execution and is now in place: WITHIN a single harness process all cells already get unique stable paths under one run-id, so parallelising cells inside one process is safe w.r.t. scratch-dir collisions WITHOUT further per-cell isolation work. Deliberately chose run-id over an flock lock precisely so this task is not serialised. NOTE: TASK-0182 added gate-only NUC_E2E_FORCE_SHARED_RUN_ID (test seam) and a 24-way concurrency stress test (tests/concurrency_stress.rs) that can be extended to assert the in-process parallel executor stays infra-race-free. Also: the end-of-run finalize_run_scratch cleans the per-run tree on success — a parallel executor must keep the single end-of-run cleanup (do NOT clean per-cell, sibling cells share the run-id root).

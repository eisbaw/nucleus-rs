## Background

TASK-0329.01 cycle-161 design analysis identified Option (D) as the smallest slice that resolves the wait-before-push deadlock on `05-stencil/distributed-2d × mp-tcp-event` (the TASK-0332 trigger cell). See TASK-0329.01 notes (Cycle 161 + Cycle 161b review fold-back) for the full 5-option analysis.

This task is **slice 1 of the TASK-0329.01 keystone split**. Sibling: TASK-0329.01.02 (Option B for in-loop case). Deferred slice 3 (Option A threaded relay) and slice 4 (Option E full w↔w mesh) per parent notes.

## Hypothesis to test (must remain falsifiable; do NOT promote to claim until tested)

If each worker's event list is rewritten so that all w2w Pushes whose payload does NOT depend on any preceding **w2w Wait result** are hoisted BEFORE the worker's w2w Waits (within a top-level boundary), AND host's relay block is moved from its current splice point (after the last top-level Sync) to BEFORE the first wait-bearing Sync ON mp-tcp-event ONLY — then the single-threaded host-relay can drain forward without entering the wait-before-push cycle that currently deadlocks at `relay_phase_insertion_point` placement.

## Acceptance criteria

### AC#1: dependency analysis (P1.1 review fold-back)

A new analysis (probably in `nucleus-compiler/src/passes/`) determines, for each w2w `Event::Push` in a worker's event list, whether its payload expression depends on any value produced by a preceding `Event::Wait` **whose `src` is a non-host worker** (a w2w Wait) in the same worker's event list. **host->worker Waits (host broadcast of input data) are NOT load-bearing dependencies for this analysis** — host's preceding events are guaranteed to have completed by the time the relay phase splices in, so a Push that depends on the host-broadcast `img_in` is still safe to hoist above w2w Waits.

The 05/distributed-2d trigger cell has exactly this shape: the worker's halo Push payload IS read from `img_in`, which the worker first waited on from host (the broadcast). Under the original AC#1 wording (any preceding Wait counts), Option (D) would have been a no-op on its target cell. The distinction between w2w-Wait and host->worker-Wait is load-bearing.

Affine-stride source-partition data with a preceding host->worker Wait dependency is hoistable. Chained transfers (Push payload computed from a preceding w2w Wait result) are NOT hoistable. Conservative: when in doubt, mark not-hoistable.

### AC#2: reordering pass

A new pass `apply_safe_push_reorder` (layer to be pinned; see AC#6) rewrites each worker's event list to hoist hoistable w2w Pushes above the worker's preceding w2w Waits within a top-level boundary (between adjacent `Event::Sync` events at depth 0, or before the first Sync, or after the last Sync). Must be safe under `Event::Loop` bodies — see honest-scope limit below.

### AC#3: relay splice-point adjustment (P1.2 review fold-back — backend-asymmetric)

**AC#3a (mp-tcp-event):** `nucleus/backends/mp-tcp-event/src/multi_worker.rs:relay_phase_insertion_point` is changed to splice the relay block BEFORE the first wait-bearing Sync (or equivalently, before bar_0 when the schedule's first Sync is wait-bearing). The mp-tcp-event reactor's per-seq-demux (`runtime_src.rs` inbound map keyed on `seq`) makes this safe — no read-races between host's relay and host's own DATA Waits.

**AC#3b (mp-tcp-bufsync — DO NOT lift):** `nucleus/backends/mp-tcp-bufsync/src/lib.rs` splice point MUST REMAIN unchanged. mp-tcp-bufsync documents constraint 3 explicitly (per cycle-148 design): "Relay reads from `data_<src>` would race host's own reads on the same socket, so relay must happen BEFORE any host Wait on a worker that also has w2w pushes." The bufsync stream is FIFO per pair, not per-seq-demuxed (cf. memory `project-mp-tcp-event-vs-bufsync-safety-profile`). Moving bufsync's splice point would re-open the cycle-148 race that constraint 3 was designed to avoid. Paired-lift discipline thus produces an ASYMMETRIC outcome here:
- mp-tcp-event: behavioral change.
- mp-tcp-bufsync: NO behavioral change. Add a code comment at the bufsync splice site forward-linking THIS task and constraint 3 with a one-line note that the asymmetry is intentional.

This is the silent-sibling-defect pattern in reverse (memory `feedback-silent-sibling-defect`): applying the same lift to a structurally-identical sibling that has a backend-specific reason NOT to take it would itself be a defect.

### AC#4: defensive guard contingency (P2.4 review fold-back — enumerate residual classes)

TASK-0332's `detect_wait_before_push_hazard` (cycle 151) MUST remain in place as a safety net. The reordering pass narrows but does NOT eliminate the wait-before-push surface. Post-AC, the guard's residual rejection classes:

- **(R1) Workers whose w2w Push payload IS dependent on a preceding w2w Wait** (genuine chained transfers — the reordering pass conservatively does NOT hoist these). The guard fires correctly; no further work needed.
- **(R2) Workers whose `Event::Loop` body contains w2w Pushes with wait-before-push order inside the loop body.** Slice 1 is OUT-OF-SCOPE for loop bodies (AC#7); the guard fires correctly here too. Resolution: slice 2 (TASK-0329.01.02 / Option B). 

Both classes' filed surfaces: residual rejection messages should be reviewed to cite the relevant follow-up (R1 → no follow-up; R2 → TASK-0329.01.02).

### AC#5: e2e promotion

`05-stencil/distributed-2d × mp-tcp-event` promotes from `[[skip]]` to `[[required]]` in `nuc-nucleus/e2e-matrix.toml`. Bit-identical against `05-stencil/reference.bin` (same oracle as the pthreads-async sibling).

### AC#6: regression pin + layer pin

Two parts:
- (i) Add a fixture exercising the reordering pass: input event list with a wait-before-push shape; assert reordered output. Also a negative fixture: input with a DEPENDENT w2w-Wait predecessor; assert the pass does NOT reorder. Also a negative fixture: input with a host->worker-Wait predecessor (NOT a w2w-Wait); assert the pass DOES reorder.
- (ii) **Layer pin (P2.1 review fold-back):** the implementer MUST choose at the start of slice 1 whether the reorder pass operates at the **ACFG layer** (pre-projection) or the **per-worker event-list layer** (post-projection). Document the choice in the pass docstring. The choice affects composition with slice 2 (TASK-0329.01.02 operates at ACFG layer; if slice 1 is at event-list layer, composition is sequential post-projection, which is fine but should be explicit). Recommendation: event-list layer for slice 1 — the analysis (does Push payload depend on preceding Wait result?) is more natural over already-projected events than over ACFG Xfer nodes. But the choice is the implementer's; just pin it.

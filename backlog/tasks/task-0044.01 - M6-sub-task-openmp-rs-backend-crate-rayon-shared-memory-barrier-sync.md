## Goal

Land the fifth tier-1 backend crate `nucleus/backends/openmp-rs`: workers map to rayon threads, transport is shared memory, notify is barrier, sync-only (no async, no buffer). PRD §7.1 row 1.

This is the SIMPLEST of the three M6 backends — same capability surface as pthreads-sync (sync + shared-memory + barrier-style notify), differing only in worker substrate (rayon scope/par_iter instead of std::thread). Because the capability matrix matches pthreads-sync 1:1, every schedule that compiles against pthreads-sync MUST compile against openmp-rs unchanged; the cross-backend differential gains a third sync-shared-memory row.

## Closest template

`nucleus/backends/pthreads-sync` is the structural template:
- Same `emit(per_worker, names, sidecar, kernels_path, out_dir)` signature.
- Same single-binary output (no run.sh process orchestration).
- Same use of `backend-common`'s `multi_worker_walker`, `check_frame`, `project_skeleton`, `render`, `host_election` helpers.

The diff is the runtime substrate: rayon's `scope` / `par_iter` instead of std::thread::spawn + handles. The barrier becomes rayon's implicit join at scope-end (or `rayon::iter::IntoParallelRefIterator::join()`).

## Capabilities

```toml

```

(Identical to pthreads-sync capability surface; only `name` differs.)

**PRD vs reality:** PRD §7.1 row openmp-rs lists notify=`barrier` and pthreads-sync notify=`condvar`. The actual `pthreads-sync/capabilities.toml` ships notify=`["barrier", "blocking"]`. This brief copies the actual cap-file convention (not the narrower PRD row), because the compat-check matches on the cap-file. If the implementer reads the PRD §7.1 row and tries to ship notify=`["barrier"]` alone, schedules currently compiling on pthreads-sync via the `"blocking"` capability arm will reject on openmp-rs. KEEP `["barrier", "blocking"]` and treat the PRD row as documentary/aspirational (a separate cycle may reconcile PRD §7.1 to the actual cap-file convention, but that is NOT this task's scope).

## Honest scope

- rayon is a new top-level dependency; needs justification (PRD §12.2 doesn't list it). The substrate is the only well-known shared-memory parallel library for Rust; the dependency is bounded (rayon → std). Note rayon's transitive deps (crossbeam, num_cpus) in the design notes.
- The 'OpenMP' in the name is metaphorical — there's no real C-OpenMP runtime, no #pragma omp parallel. The name signals 'parallel-for shared-memory' semantics, matching how rayon is used in practice.
- multi-worker semantics: where pthreads-sync's multi_worker arm spawns N std::threads with Condvar rendezvous, openmp-rs uses rayon::scope with channel-based rendezvous (or shared Mutex if the rendezvous shape forces it). The backend-common multi_worker_walker abstracts much of this — check whether its rendezvous_prefix mechanism extends to rayon or needs a new arm.

## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
PRD §8 promises: same source + same backend = same emitted code, byte-for-byte. Add a CI check that compiles every (example, schedule, backend) twice and diffs the generated source.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
## Design questions explored

**Strip timestamps before diff vs eliminate them in codegen.** The TASK-0033 brief flagged "timestamp comments" as a thing to consider stripping. I audited the four files the pthreads-sync codegen emits — `Cargo.toml`, `run.sh`, `src/main.rs`, `src/kernels.rs` — and confirmed *none* of them carry a wall-clock timestamp. The PRD §1 promise is honoured by codegen, not by a downstream strip pass. The harness therefore does a *raw byte diff* with zero exceptions; if future codegen ever adds a timestamp, the determinism check fails loud (correct behaviour: file a fix in the codegen, not a strip rule in the harness). Documented in the source comments above `check_cell_determinism`.

**Capability-mismatch / build-failure = SKIPPED, not FAILED.** Determinism mode treats any cell where the harness can't actually invoke `nucleus build` twice as SKIPPED, not FAILED. Rationale: PRD §1 promises byte-identity *for cells that compile*; a cell that the compiler rejects is out of scope for the determinism contract. Run-mode reports the same condition as Failed(Compile) because that's what the run-mode contract demands; the two modes therefore disagree on the same input, by design. This is documented in the module comment.

**Diff every file, including the Cargo.toml.** AC #5 of TASK-0033 listed "whether to include the Cargo.toml in the byte-diff" as an open question. I include it. The Cargo.toml is part of the codegen output that the user inspects; if the manifest's keys reorder per run (TOML serialisers can do that under the wrong configuration), the user's diff tooling would also see noise. Better to catch it here. Empirically the current pthreads-sync emitter writes Cargo.toml with hand-formatted literal strings, so it is stable; the check guards against a future regression.

**No Cargo.lock comparison.** Cargo.lock is generated by `cargo build`, not by the nucleus pipeline. The determinism check runs only `nucleus build` (phase 1), so no Cargo.lock is emitted and there's nothing to diff. If a future tier of the e2e harness materialises a Cargo.lock as part of the determinism scope, it would belong in a separate cell type ("reproducible-deps" check).

**BTreeSet on relative paths for diff order.** The harness walks each out-dir with a stack-based recursion that yields paths in filesystem order (non-deterministic across runs). To make the failure surface itself deterministic, the diff sorts via BTreeSet on relative paths. Without this, two failures on the same matrix could report different offending files run-to-run, which would defeat the point of the test.

**Parallel cell execution.** Same trade-off as TASK-0023.01 in run-mode: sequential is fine for ten cells × ~300ms each. Filed implicitly under TASK-0023.01 — the parallelisation work for the run-mode harness would naturally extend here.

## Honest limitations

- **Only the Rust source files emitted by codegen are checked.** Cargo.lock is not produced or compared. `target/` is never touched in determinism mode. Determinism of the compiled binary (which depends on rustc, codegen flags, build-script environment, and the resolver's lock state) is a different problem — "reproducible builds" — and is out of scope for TASK-0033 / PRD §1.
- **Only verifies codegen, not running binary output.** Two byte-identical codegen outputs that produce divergent runtime output would be caught by `just e2e`, not by `just determinism-check`. The two checks layer; `determinism-check` is upstream of `e2e`.
- **AC #4 negative-test deferred to TASK-0145.** The acceptance criterion asked for a deliberate-nondeterminism injection (e.g. a HashMap iteration in codegen) that proves the determinism check fails loud. The TASK-0033 PR ships only the positive arm — "deterministic codegen produces PASS". The negative arm is filed as **TASK-0145** because it touches the pthreads-sync backend with a feature gate; clean-keeping it as a separate task lets TASK-0145 ship a synthetic-failure-and-cleanup pair without the determinism check itself changing.
- **The harness invokes `cargo run --bin nucleus -- build` twice per cell**, which means each invocation goes through cargo's incremental rebuild path. A pathologically misconfigured cargo cache could in principle suppress a real source-code change between the two runs (cargo would not re-run the binary). In practice cargo is sound on this; the harness clears the per-cell out dirs to ensure the two builds genuinely re-emit. Not a known-broken corner, but documented for completeness.
- **A cell whose run-mode counterpart is FAILED-due-to-compile still reports SKIPPED here.** The two modes deliberately disagree (see design notes). A reviewer who reads only the determinism summary should also check the run-mode summary to see whether any cell is failing to compile entirely.
- **No stable-snapshot test.** TASK-0033 does not pin the bytes of the emitted code against a checked-in golden snapshot. "Two consecutive runs agree" is a strictly weaker claim than "the output matches the committed reference". The latter would catch regressions across PRs; this only catches nondeterminism *within* one PR. Filed mentally; not a backlog task yet because the value-add of golden snapshots is a separate design decision (they couple test data to codegen format, which makes innocuous codegen refactors loud).

## Outcome

Did all currently-PASSing cells produce byte-identical codegen on two runs? **Yes**: 6/6 PASS, ~282–332ms per cell (single `nucleus build` invocation × 2). No nondeterminism found in the pthreads-sync codegen across the M1 matrix; the codegen authors' explicit BTreeMap/BTreeSet discipline (TASK-0020, TASK-0122) paid off. The determinism check is therefore *enforcing a property that currently holds*, not *flagging an outstanding bug*.

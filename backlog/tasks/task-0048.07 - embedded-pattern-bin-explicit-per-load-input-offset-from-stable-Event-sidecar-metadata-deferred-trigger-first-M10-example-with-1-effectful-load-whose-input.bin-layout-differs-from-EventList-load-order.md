## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Deferred-trigger follow-up split from TASK-0048.06 (which verified the implicit cursor is CORRECT for all 3 current M10 examples: ex1 two-load a++b matches source/EventList order, ex5/ex9 single-load trivial). The Usart1Shim/axiSram injected-input cursor advances by each effectful load's byte length in EventList load order, ASSUMING input.bin is the concatenation of the loaded arrays in that same order. This holds for every in-tree M10 example today. It BREAKS the first time an M10 example has >1 effectful load whose input.bin byte layout does NOT match EventList load order (e.g. input.bin authored array-B-first while the algorithm loads A then B). Remediation when that example lands: replace the implicit length-advancing cursor with an EXPLICIT per-load byte offset derived from a stable source (NameSidecar or Event metadata), NOT kernel-body parsing. Mirror the TASK-0111->TASK-0347 close-deferred / reopen-on-fire pattern. AC: (1) the firmware reads each load's slice via an explicit offset table keyed by the same stable id the EventList uses; (2) a regression example/fixture with deliberately mismatched input.bin order proves the byte-exact reference.bin cmp still passes.

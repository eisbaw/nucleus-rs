## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Forward-carried from TASK-0389. The TASK-0389 root fix sorts each worker's per-channel Wait sequence by producer_rank_by_data (raw producer-Operation walk position). That EXACTLY matches the host's per-channel Push order for the common case (host load producers / same-scope producers — all host->worker load channels, the entire gather/scatter family). splice_pushes_global, however, can HOIST a loop-OUTPUT producer's Push out past its enclosing Repeat (the 'cut' branch). If two data on the same channel have producers at different nesting whose Pushes hoist to different positions vs producer rank, the worker's producer-rank sort could still diverge from the host's effective send order. VERIFIED NO in-tree schedule exercises this: 06-separable-filter/distributed2 (loop-output cross-worker) and 03-reduction/distributed (4-partial gather) are byte-identical pre/post the TASK-0389 sort across pthreads-sync/mp-tcp-bufsync/mp-tcp-poll/mp-uds-event. This task either (a) constructs the bite-test and refines the key to the post-splice position, or (b) proves the cut-hoist preserves per-channel rank order and closes the residual. Code anchor: the 'SCOPE of the producer-rank key' comment in build_waits_for_op (transfer_inject.rs) references this id.

## Implementation Notes

AC#2 BRANCH: (a) REAL-BUG + FIX. The residual is NOT vacuous.

CRUX (empirical, not narrative). splice_after_repeat inserted each cut-hoisted Push IMMEDIATELY after the enclosing Repeat. collect_waits returns Waits in DFS order; splicing each Push re-walks the already-mutated tree and lands it closest-to-the-Repeat, so co-hoisted Pushes end up in REVERSE collect_waits order. A unit test (task038901_crux_cohoisted_pushes_textual_order_vs_rank) built an ACFG with two loop-output data a,b produced inside one Repeat, both consumed at top-level on one w0->host channel; PRE-FIX it printed post-splice Push textual order [b,a] vs producer_rank order [a,b]. The host therefore SENDS reverse-rank while build_waits_for_op makes the worker WAIT rank-order => strict-FIFO divergence.

AC#1 fixture: NEW example 18-multigather. Single compute worker w0 produces p (=2a) then q (=3a) inside one for-i loop; host save_pq consumes both AFTER the loop. distributed.sched.nuc => p,q are TWO loop-outputs on ONE (w0->host) channel, both cut-hoist past the for-i Repeat. Constructible reason no in-tree cell hit it before: 03-reduction gather partials are per-worker (separate src per channel, multiplicity 1) and 06-sep-filter/distributed2 routes only ONE intermediate (tmp) w<->w (multiplicity 1). 18-multigather is the first cell with per-channel multiplicity >=2 for loop-outputs.

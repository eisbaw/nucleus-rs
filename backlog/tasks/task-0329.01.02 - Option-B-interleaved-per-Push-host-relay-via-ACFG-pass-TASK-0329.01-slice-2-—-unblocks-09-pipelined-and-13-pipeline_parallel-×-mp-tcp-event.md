## Background

TASK-0329.01 cycle-161 design analysis identified Option (B) as the slice that resolves the **in-loop w2w Push** deadlock on the two remaining trigger cells:
- `09-producer-consumer/pipelined × mp-tcp-event` (per-iter Push in `for n in 0..16`).
- `13-cnn-inference/pipeline_parallel × mp-tcp-event` (per-batch inter-stage transfer in pipelined outer loop).

This task is **slice 2 of the TASK-0329.01 keystone split** (slice 1 is TASK-0329.01.01 / Option D). Per cycle-161b review, this slice may be further split into 09-only validation (TASK-0329.01.02.01 if filed) + 13-only promotion (TASK-0329.01.02.02 if filed) per P3.2 review note.

## Hypothesis to test (must remain falsifiable; do NOT promote to claim until tested)

The cycle-160 precedent (compiler-level CTRL-arm lift via `host_mediation_inject` pass) showed that ACFG-level injection of host participation is structurally clean for `Sync` participants. The DATA-arm analogue is **NOT** structurally analogous in a one-to-one sense (cycle-161b review P1.3 fold-back): cycle-160's pass mutates a `BTreeSet<WorkerId>` field on existing `Sync` nodes additively; this task's pass either adds new ACFG nodes (B1) or expands one `Xfer` into four (B2). Both require seq-allocator state + projection-side handling that cycle-160 did not.

## Acceptance criteria

### AC#1: pick a variant and pin its semantics (P1.3 review fold-back — required additions)

Pick ONE of (B1) or (B2) and document in the pass docstring. The choice must address ALL of the following:

#### (B1) New ACFGNode::Relay variant
- Introduce `ACFGNode::Relay { src, dst, data, seq, tile }` as a new ACFG variant. The pass walks every `Xfer` with non-host endpoints and emits a `Relay` node BEFORE the existing Push/Wait pair, structurally positioned to project onto host's per-worker event list at the right depth.
- **Match-exhaustiveness audit (required):** Run a full grep audit of `match` arms on `ACFGNode` (including in `acfg_to_events`, `host_mediation_inject`, `transfer_inject`, `sync_inject`, any analysis passes). Enumerate every site. Add a handler for `Relay` at each.
- **Projection-side handling:** `acfg_to_events` at `petri_to_events.rs:330-358` skips workers whose body_events is empty under `Repeat` projection. The Relay node must contribute a non-empty event to host's per-worker list at the Repeat body site — verify the projector emits an event for host (e.g. via host being a participant in the Relay's participants set, or by Relay projecting unconditionally for the host endpoint).

#### (B2) ACFG mutation: route Xfer through host (no new variant)
- For each `Xfer { src=w_src, dst=w_dst, role=Push, seq=s, ... }` with `w_src != host && w_dst != host`, replace with FOUR Xfer nodes: Push src->host (new seq s1), Wait host<-src (seq s1), Push host->dst (new seq s2), Wait dst<-host (seq s2).
- **Seq allocator integration (required):** The current seq allocator state is not exposed to a new pass. Either expose it (via a `&mut SeqAllocator` parameter threaded through the pass entry point and into `ACFG`), or use a deterministic-function rule (e.g. `s1 = s * 2`, `s2 = s * 2 + 1`) with sidecar verification of uniqueness. Document the choice.
- **Match-exhaustiveness audit (required):** Even though no new variant lands, the structural shape of the ACFG changes; verify every pass that walks `Xfer` handles the routed shape (especially `transfer_inject` and `sync_inject`).

### AC#2: in-loop case works

`09-producer-consumer/pipelined × mp-tcp-event`: the per-iter Push inside `for n in 0..16` projects to host's event list as a per-iter Relay event inside host's `Event::Repeat` body. Each iteration's relay drains the worker's outbound queue, preventing back-pressure deadlock.

### AC#5: paired-lift to mp-tcp-bufsync (P2.3 review fold-back — bufsync FIFO ordering audit required)

mp-tcp-bufsync has the same TASK-0330 defensive guard (`nucleus/backends/mp-tcp-bufsync/src/lib.rs:1690-1704`). The structural pass site is shared; the (B) lift applies at the ACFG level (compiler pass).

**However: runtime behavioral verification on bufsync is NOT automatic.** mp-tcp-bufsync's per-pair single FIFO stream + `wire::read_msg_expect` panic-on-seq-mismatch (memory `project-mp-tcp-event-vs-bufsync-safety-profile`) has ordering hazards that mp-tcp-event's per-seq-demux does not. If (B) generates per-iter host Pushes/Waits on a FIFO stream, bufsync may panic on shapes mp-tcp-event tolerates. The bufsync FIFO ordering hazard MUST be audited before claiming structural sufficiency.

Bufsync's 09/13 cells are capability-gated on async/buffer/event so e2e promotion is bufsync-deferred regardless; but the bufsync structural pass MUST be audited to confirm it does not introduce a latent panic surface on future capability-compatible schedules.

### AC#6: composition with slice 1 (P2.1 review fold-back — pin layers)

Slice 1 (TASK-0329.01.01) pins its layer in its own AC#6 (event-list-layer recommended). Slice 2 operates at the **ACFG layer** (pre-projection). Composition: slice 1 transforms post-projection events; slice 2 transforms pre-projection ACFG. They are at different layers and therefore commute trivially. Pin in this task's docstring: "this pass runs at the ACFG layer, before `acfg_to_events`; slice 1's reorder pass runs at the event-list layer, after `acfg_to_events`."

If the implementer instead moves slice 1 to ACFG layer (its AC#6 (ii) allows the choice), the composition order is "slice 2 first (synthesize relay nodes recursively under Repeat), then slice 1 (reorder hoistable Pushes at top level)" — slice 1 only operates at depth 0, so its reordering would not touch the per-iter relay events slice 2 emitted inside Repeat bodies.

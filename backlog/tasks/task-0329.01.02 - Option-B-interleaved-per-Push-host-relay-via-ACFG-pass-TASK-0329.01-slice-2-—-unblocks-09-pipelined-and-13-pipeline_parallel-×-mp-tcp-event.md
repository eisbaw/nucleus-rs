## Background

## Hypothesis to test (must remain falsifiable; do NOT promote to claim until tested)

The cycle-160 precedent (compiler-level CTRL-arm lift via `host_mediation_inject` pass) showed that ACFG-level injection of host participation is structurally clean for `Sync` participants. The DATA-arm analogue is **NOT** structurally analogous in a one-to-one sense (cycle-161b review P1.3 fold-back): cycle-160's pass mutates a `BTreeSet<WorkerId>` field on existing `Sync` nodes additively; this task's pass either adds new ACFG nodes (B1) or expands one `Xfer` into four (B2). ### Forward-carried lesson F1 — Splice algorithm divergence latent risk

Slice 1 rewrote `nucleus/backends/mp-tcp-event/src/multi_worker.rs:relay_phase_insertion_point` to walk Syncs by `SyncTag` and return the first all-w2w-done Sync. On all currently-passing mp-tcp-event cells with 2 barriers, the algorithm is byte-identical with the cycle-149 LAST-Sync heuristic. **It is NOT identity on 3+ barrier cells.**

The slice-1 algorithm only scans TOP-LEVEL events at `w_events[w_sync_idx..]` — it does NOT recurse into `Event::Loop` bodies. Slice 2's target cells (09/pipelined, 13/pipeline_parallel) have w2w Push events INSIDE Loop bodies. A naive reuse of slice-1's splice algorithm would treat Loop body w2w activity as invisible: `has_post_w2w = false` at every Sync, so the splice would land BEFORE the Loop body executes, before the Loop body's w2w activity has anything to relay.

**Implementer guidance**: do not assume mechanical reuse of `relay_phase_insertion_point`. The per-Push relay-inject design (Option B) needs its own splice or per-iteration relay-event-placement semantics. The cycle-149 LAST-Sync fallback might be the right answer here (relay synthesises into the Loop body itself, so host's relay event is co-located with the worker's Push by structural projection — no splice needed at top level).

### Forward-carried lesson F2 — Per-event-variant write enumeration

Slice 1 cycle 162a empirically discovered (via e2e gate failure on 06/distributed2) that the hoistable predicate must consider Fire writes (`bindings.output`) AND host->worker Waits (conservatively), not just w2w Waits as cycle-161 design listed. The slice-1 unit fixtures missed this because the cycle-161 design didn't enumerate Fire writes as dependencies; the unit tests covered the gaps that cycle-161 thought of, not the gaps the real schedule exposes.

**Implementer guidance**: when slice 2's pass synthesises new ACFG nodes or rewrites Xfer routing, enumerate EVERY event variant that can write data (Fire output, w2w Wait, host->worker Wait, Loop body recursive). Test against the FULL e2e matrix, not just unit tests. Memory `feedback-orchestrator-narrative-also-wrong` 12th firing (cycle 162a entry) details the structural-vs-codegen mismatch shape.

### Forward-carried lesson F3 — Worker event projections are NOT uniform

Slice 1's empirical observation: pthreads-async's emit for 05/distributed-2d shows w0 has [Wait, Wait, Push, Push, bar_0] but w1 has [Push, Wait, Wait, Push, bar_0]. Different workers may have different Push/Wait orderings naturally. Slice 1's reorder operates per-worker independently, which handles this naturally.

**Implementer guidance**: slice 2's ACFG-level relay-inject pass produces per-worker projections via `acfg_to_events`. Each worker's projection is generated independently — the pass's invariant must hold per-worker, not uniformly. Slice 1's per-boundary independence is the precedent.

**Implementer guidance**: slice 2's per-Push relay-inject pass is at the ACFG layer (per AC#6 of TASK-0329.01.02). ## Cycle 163 implementation plan

### Variant choice: B2 (ACFG Xfer routing) — picked deliberately over B1

**Decision rationale (B1 vs B2):**

B1 (new `ACFGNode::Relay` variant) requires:
- Audit of ~17 distinct `match` sites on `ACFGNode` repo-wide (counted via `rg 'match.*node\s*\{' nucleus-compiler/src/passes/ + sidecar.rs + acfg_to_petri.rs`).
- New projection arm in `petri_to_events.rs:walk` to emit a host-side event in the Repeat body.
- New semantics for downstream walkers (block_transform, partition_*, sync_inject) — most would just no-op the new variant, but the structural-correctness audit at each is non-trivial.

B2 (rewrite Xfer pair to 4 Xfers via host) keeps the variant set fixed:
- Pre-walk to find `max_seq` in the ACFG (cheap; one pass).
- For each `Xfer{role=Push, src≠host, dst≠host}` paired with its sibling Wait, replace both with FOUR `Xfer`s: (Push src→host, s1), (Wait host←src, s1), (Push host→dst, s2), (Wait dst←host, s2). Both new pairs use fresh seqs derived from max_seq+counter (deterministic + unique).
- The TransferPolicy + tile clone forward to every new Xfer.
- The sidecar's `transfer_buffer_for_seq` map needs an entry for each new seq (clone the original seq's buffer).
- ACFG sidecar maps that are SeqTag-keyed (pipeline_depth_for_seq) need cloned entries for new seqs.
- Match-exhaustiveness audit is **structurally vacuous** — no new variant, so every walker already handles `ACFGNode::Xfer`.

**Critical-path observation that made B2 unambiguously cleaner:**
The existing `render_worker_events` + `collect_pre_init_sets` + `collect_worker_rendezvous` machinery (`backend-common/src/multi_worker_walker.rs`) ALREADY recurses into Loop bodies and ALREADY allocates per-worker locals + Chan IDs for Wait/Push endpoints. So adding host as a Wait+Push endpoint via B2 produces correct host-side codegen WITHOUT touching the renderer — host's projected body gets a Loop event with body=[Wait stream, Push stream], rendering as `for n in 0..16 { stream = chan_X.wait(); chan_Y.push(stream.clone()); }`. The cycle-149 flat `render_relay_phase` becomes a no-op because there are no top-level w2w Pushes left after the rewrite (the original in-loop pair has been routed through host's Loop body instead).

### Cycle-163 empirical refinement — load-bearing scope limit

The first cycle-163 draft (Phase 2 of `rewrite_at`) rewrote EVERY non-host-pair Push/Wait — top-level AND in-Repeat-body. The e2e gate caught a 05-stencil/distributed-2d × mp-tcp-event regression (first byte differs at offset 0x58, sha256 c7927bb... vs ref 2e405a3...):

The cycle-149 flat host-relay ALREADY handles them via `relay_one(seq, dst_peer, cap)` + tile-aware `render_wait_assign`.

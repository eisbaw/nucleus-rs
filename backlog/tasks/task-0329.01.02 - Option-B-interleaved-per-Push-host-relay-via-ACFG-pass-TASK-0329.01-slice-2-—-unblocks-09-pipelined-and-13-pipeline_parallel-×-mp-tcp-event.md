## Background

TASK-0329.01 cycle-161 design analysis identified Option (B) as the slice that resolves the **in-loop w2w Push** deadlock on the two remaining trigger cells:
- `09-producer-consumer/pipelined × mp-tcp-event` (per-iter Push in `for n in 0..16`).
- `13-cnn-inference/pipeline_parallel × mp-tcp-event` (per-batch inter-stage transfer in pipelined outer loop).

Both are currently rejected at codegen by the TASK-0330 defensive guard (cycle 153: `collect_w2w_pushes` walking into `Event::Loop` bodies fails-loud).

This task is **slice 2 of the TASK-0329.01 keystone split** (slice 1 is TASK-0329.01.01 / Option D). Per cycle-161b review, this slice may be further split into 09-only validation (TASK-0329.01.02.01 if filed) + 13-only promotion (TASK-0329.01.02.02 if filed) per P3.2 review note.

## Hypothesis to test (must remain falsifiable; do NOT promote to claim until tested)

The cycle-160 precedent (compiler-level CTRL-arm lift via `host_mediation_inject` pass) showed that ACFG-level injection of host participation is structurally clean for `Sync` participants. The DATA-arm analogue is **NOT** structurally analogous in a one-to-one sense (cycle-161b review P1.3 fold-back): cycle-160's pass mutates a `BTreeSet<WorkerId>` field on existing `Sync` nodes additively; this task's pass either adds new ACFG nodes (B1) or expands one `Xfer` into four (B2). Both require seq-allocator state + projection-side handling that cycle-160 did not.

## Acceptance criteria

### AC#1: pick a variant and pin its semantics (P1.3 review fold-back — required additions)

Pick ONE of (B1) or (B2) and document in the pass docstring. The choice must address ALL of the following:

#### (B1) New ACFGNode::Relay variant
- Introduce `ACFGNode::Relay { src, dst, data, seq, tile }` as a new ACFG variant. The pass walks every `Xfer` with non-host endpoints and emits a `Relay` node BEFORE the existing Push/Wait pair, structurally positioned to project onto host's per-worker event list at the right depth.
- **Match-exhaustiveness audit (required):** Run a full grep audit of `match` arms on `ACFGNode` (including in `acfg_to_events`, `host_mediation_inject`, `transfer_inject`, `sync_inject`, any analysis passes). Enumerate every site. Add a handler for `Relay` at each.
- **Projection-side handling:** `acfg_to_events` at `petri_to_events.rs:330-358` skips workers whose body_events is empty under `Repeat` projection. The Relay node must contribute a non-empty event to host's per-worker list at the Repeat body site — verify the projector emits an event for host (e.g. via host being a participant in the Relay's participants set, or by Relay projecting unconditionally for the host endpoint).

#### (B2) ACFG mutation: route Xfer through host (no new variant)
- For each `Xfer { src=w_src, dst=w_dst, role=Push, seq=s, ... }` with `w_src != host && w_dst != host`, replace with FOUR Xfer nodes: Push src->host (new seq s1), Wait host<-src (seq s1), Push host->dst (new seq s2), Wait dst<-host (seq s2).
- **Seq allocator integration (required):** The current seq allocator state is not exposed to a new pass. Either expose it (via a `&mut SeqAllocator` parameter threaded through the pass entry point and into `ACFG`), or use a deterministic-function rule (e.g. `s1 = s * 2`, `s2 = s * 2 + 1`) with sidecar verification of uniqueness. Document the choice.
- **Match-exhaustiveness audit (required):** Even though no new variant lands, the structural shape of the ACFG changes; verify every pass that walks `Xfer` handles the routed shape (especially `transfer_inject` and `sync_inject`).

## Forward-carried from TASK-0329.01.01 (slice 1) cycle 162 + 162a + 162b

Cycle 162 + 162a landed slice 1; cycle 162b parallel review surfaced two slice-2 risks worth pinning here before implementation starts.

### Forward-carried lesson F1 — Splice algorithm divergence latent risk

Slice 1 rewrote `nucleus/backends/mp-tcp-event/src/multi_worker.rs:relay_phase_insertion_point` to walk Syncs by `SyncTag` and return the first all-w2w-done Sync. On all currently-passing mp-tcp-event cells with 2 barriers, the algorithm is byte-identical with the cycle-149 LAST-Sync heuristic. **It is NOT identity on 3+ barrier cells.**

The slice-1 algorithm only scans TOP-LEVEL events at `w_events[w_sync_idx..]` — it does NOT recurse into `Event::Loop` bodies. Slice 2's target cells (09/pipelined, 13/pipeline_parallel) have w2w Push events INSIDE Loop bodies. A naive reuse of slice-1's splice algorithm would treat Loop body w2w activity as invisible: `has_post_w2w = false` at every Sync, so the splice would land BEFORE the Loop body executes, before the Loop body's w2w activity has anything to relay.

**Implementer guidance**: do not assume mechanical reuse of `relay_phase_insertion_point`. The per-Push relay-inject design (Option B) needs its own splice or per-iteration relay-event-placement semantics. The cycle-149 LAST-Sync fallback might be the right answer here (relay synthesises into the Loop body itself, so host's relay event is co-located with the worker's Push by structural projection — no splice needed at top level).

### Forward-carried lesson F2 — Per-event-variant write enumeration

Slice 1 cycle 162a empirically discovered (via e2e gate failure on 06/distributed2) that the hoistable predicate must consider Fire writes (`bindings.output`) AND host->worker Waits (conservatively), not just w2w Waits as cycle-161 design listed. The slice-1 unit fixtures missed this because the cycle-161 design didn't enumerate Fire writes as dependencies; the unit tests covered the gaps that cycle-161 thought of, not the gaps the real schedule exposes.

**Implementer guidance**: when slice 2's pass synthesises new ACFG nodes or rewrites Xfer routing, enumerate EVERY event variant that can write data (Fire output, w2w Wait, host->worker Wait, Loop body recursive). Test against the FULL e2e matrix, not just unit tests. Memory `feedback-orchestrator-narrative-also-wrong` 12th firing (cycle 162a entry) details the structural-vs-codegen mismatch shape.

### Forward-carried lesson F3 — Worker event projections are NOT uniform

Slice 1's empirical observation: pthreads-async's emit for 05/distributed-2d shows w0 has [Wait, Wait, Push, Push, bar_0] but w1 has [Push, Wait, Wait, Push, bar_0]. Different workers may have different Push/Wait orderings naturally. Slice 1's reorder operates per-worker independently, which handles this naturally.

**Implementer guidance**: slice 2's ACFG-level relay-inject pass produces per-worker projections via `acfg_to_events`. Each worker's projection is generated independently — the pass's invariant must hold per-worker, not uniformly. Slice 1's per-boundary independence is the precedent.

### Forward-carried lesson F4 — Bufsync paired-lift is structurally asymmetric

Slice 1's AC#3b discovered that mp-tcp-bufsync's `relay_phase_insertion_point` MUST stay unchanged (FIFO-per-pair stream + constraint 3). The cycle-160 host_mediation_inject precedent applied symmetrically because that pass is at the ACFG layer (above the backend split); slice 1's splice change was at the backend layer (below the split), explaining the asymmetry.

**Implementer guidance**: slice 2's per-Push relay-inject pass is at the ACFG layer (per AC#6 of TASK-0329.01.02). By being at the ACFG layer, the pass's effect on bufsync vs mp-tcp-event is automatically symmetric (both backends consume the same projected event lists). BUT — the runtime behaviour may differ: bufsync's `wire::read_msg_expect` panic-on-seq-mismatch (memory `project-mp-tcp-event-vs-bufsync-safety-profile`) may fire on per-iter relay shapes that mp-tcp-event tolerates. AC#5 explicitly calls out this audit requirement.

### Forward-carried lesson F5 — The slice-1 latent-risk that the architect P1.1 surfaced

The architect review of slice 1 noted that for 05/distributed-2d, the halo Push/Wait pairs are SEMANTICALLY DEAD: they ship zero bytes pre-bar_0; the host broadcast post-bar_0 (via TASK-0263 tile-extension) overwrites the halo region with the correct data. pthreads-async also passes for this same reason.

**Implementer guidance**: for slice 2's target cells (09/pipelined, 13/pipeline_parallel), the in-loop w2w transfers are NOT semantically dead — they carry per-iteration computed data that the receiver needs. The slice-1 redundancy argument does NOT carry forward. Each iteration's Push payload IS computed by some preceding Fire; the relay must place the host-mediated forward AFTER that Fire.

This means slice 2's pass cannot be a simple "always synthesise host-mediated relay early" — it must respect the per-iteration dependency graph. The Option (B1) new `ACFGNode::Relay` variant approach lets the ACFG carry the structural relationship; the (B2) four-Xfer expansion would need explicit ordering constraints.

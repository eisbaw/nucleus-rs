## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-0382 cycle-221 landed check-doc-citation-staleness-bare: a crate-scoped, prose-aware resolver for bare <file>.rs:N citations (zero-FP, wired into just ci). Two SAFE coverage gaps were deferred (both currently fall to SKIP — neither can produce a false POSITIVE, they just go unvalidated):

(1) PARTIAL-PATH citations like multi_worker/mod.rs:N, sched/ir.rs:N, multi_worker_walker/event_walker.rs:N. The cycle-221 resolver discards the path prefix and resolves the BASENAME only, so partial-path forms hit SKIP:ambiguous (e.g. nucleus-compiler has algo/ir.rs AND sched/ir.rs) or SKIP:basename-not-in-crate (mod.rs find-name is ambiguous/none). A prefix-honouring resolver (resolve <prefix>/<base>.rs relative to <crate-root>/src/, then range-check) would recover this coverage with NO loss of zero-FP — the interior slash is MORE disambiguating, not less. Concrete uncaptured-but-valid in-tree examples: multi_worker/mod.rs:273-284 (mp-tcp-event tests), sched/ir.rs:382 (nucleus-compiler tests).

(2) BARE-BASENAME-AS-LOCATION with NO :N (TASK-0382 Implementation Notes variant). A prose claim like "pinned by bin_rejects_multi_worker_* in tests.rs" names a file but no line; the cycle-221 fence only sees <base>.rs:N forms, so it is structurally blind. Catching it needs symbol/test-name RESIDENCE checking (does the named test still live in the cited basename?), not a line-count. This is the lie-shape TASK-0383 split freshly produced and that was caught only by manual silent-sibling grep. Harder to make zero-FP (prose ambiguity about what is a symbol name); design carefully or keep deferred.

NEITHER gap is an FP risk on the current fence; this is purely additive coverage. Lower priority than keeping the fence zero-FP.

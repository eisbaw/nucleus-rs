## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Filed from the TASK-0048.11 de-risk SPIKE (commit f08fbcc), which empirically PROVED (Renode capture + negative control, both reviews GO) that Renode's stm32h743 model drives a real DMA1 MemoryToPeripheral USART1 TX end-to-end (tests/renode/dma-uart-smoke/ + just renode-dma-uart-smoke). This task would replace the embedded-pattern Usart1Shim::dma_push CPU-store loop (which currently reads a Renode-injected axiSram region and writes USART1 TDR via the CPU) with a real DMA-controller-driven push, mirroring the proven dma-uart-smoke register sequence (DMA1 stream PAR=USART1.TDR, M0AR=src, NDTR=len, DIR=MemToPeriph|MINC, EN; CR1=UE|TE load-bearing). FORWARD-CARRIED FINDINGS (TASK-0048.11): (1) STM32DMA fires MemToPeriph immediately on EN — no peripheral request wire / DMAMUX routing needed for TX (the usart1->dmamux1 line is absent in the .repl and irrelevant). (2) DmaEngine writes every byte to the FIXED TDR with PINC=0; CR3 DMAT is a no-op flag under Renode. (3) The DMA source buffer MUST live in a DMA-accessible region (axiSram/SRAM) NOT DTCM — on real H7 silicon DMA1/DMA2 cannot reach DTCM; Renode papers over this (models DTCM as plain MappedMemory). The current memory.x links output buffers in DTCM, so a real-DMA shim needs the output array relocated to a DMA-reachable region (a non-trivial codegen/linker change). EXPLICIT AC#1-RESCOPE DECISION (architect cycle review P2): parent TASK-0048 AC#1 literally says the shim 'provides DMA controller, IRQ bindings, memory layout'. The current synchronous shim provides none of a real DMA *controller* — it is a CPU store loop. We CONSCIOUSLY NARROW AC#1 for the M10 DoD: the synchronous shim is a sufficient HONEST M10 state because on a non-cycle-accurate emulator a real-DMA push yields the SAME captured bytes with no additional VERIFIABLE fidelity (Renode fires synchronously on EN; TXE hardwired true; no async overlap to validate). NUANCE: the DMA completion-IRQ EVENT (TCIF flag + UpdateInterrupt) IS modelled and DOES fire in STM32DMA.cs — so 'IRQ bindings' is partially testable; only the async TIMING is unverifiable here. This task is therefore a HW-faithfulness upgrade, deliberately LOW priority and NOT a blocker for closing M10.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
FORWARD-CARRY from TASK-0438.02 (landed 2026-06-05): the codegen seam for a real DMA engine now exists. NucleusShim gained 3 DEFAULT methods (NUCLEUS_SHIM_SRC in embedded-pattern/src/skeleton/mod.rs): dma_link_arm / dma_link_recv_arm (default delegate to link_push/link_recv) + dma_link_poll (default returns true = synchronous-completion model). A mode=dma transfer edge emits arm + `while !dma_link_poll(seq) { spin_loop() }`. To make this a REAL DMA1 MemoryToPeripheral USART1 TX, override these three on the concrete shim: dma_link_arm programs the DMA descriptor + starts the channel (non-blocking), dma_link_recv_arm arms the RX side, and dma_link_poll reads the real DMA transfer-complete flag (TCIF) — the generated spin loop then becomes a genuine completion-wait instead of a no-op single iteration. No codegen change needed in .12; it is purely a shim-impl override. Honest caveat carried from .02: today the bytes ride the SAME UART fabric via the link_* delegate (modelled DMA shape, not silicon DMA).

forward-carried from TASK-0438.03 (2026-06-05): the M11 DMA+PIO demo (22-dma-pio-demo) is now byte-exact under Renode with the MODELLED DMA — dma_link_arm delegates to link_push and dma_link_poll returns true synchronously, so the emitted `while !shim.dma_link_poll(seq) { spin_loop(); }` completion loop terminates on its FIRST iteration. When this task wires the REAL DMA1 MemoryToPeripheral USART1 TX engine, the link-transport DMA hooks (dma_link_arm / dma_link_recv_arm / dma_link_poll) have the SAME hazard as the dma_push path: dma_link_poll MUST be overridden to read the silicon transfer-complete / DMA-stream-status bit, NOT the default `true`. If left at the default, the spin loop races a real async transfer (reads the buffer before the stream finishes) and the byte-exact proof silently breaks. The demo currently proves VALUE-correctness only (parent TASK-0438 AC#4); a real engine here is what would let it also demonstrate timing (CPU does work while the stream runs).

AC#3 — TCIF / real-vs-Renode fidelity (verified against Renode 1.16.1 STM32DMA.cs):
- TCIF IS modelled + DOES get SET on completion. STM32DMA.cs HandleEnable (line 241) -> PerformTransfer (line 247): for direction != PeripheralToMemory the WHOLE transfer runs SYNCHRONOUSLY on the EN write (IssueCopy), and when nrOfData hits 0 it sets transferCompleteIrqStatus[id].Value = true (TCIF) + calls UpdateInterrupts() (line ~258-263).
- BUT the completion IRQ LINE only asserts if TCIE (TransferCompleteIrqEnable, SxCR bit4) is set (UpdateInterrupts gates on stream.TransferCompleteIrqEnable && TCIF, line 133). Our shim leaves TCIE=0 and does NOT wire the DMA1 stream0 IRQ vector, so no IRQ HANDLER fires — by design. We never wait on TCIF because the transfer is already complete by the time the EN write returns (synchronous-on-EN model). So: TCIF flag = SET (modelled), IRQ line/handler = NOT wired (deliberate), and dma_wait is a correct no-op here.
- FIDELITY LIMITS (real silicon vs Renode): (1) synchronous-on-EN — Renode performs the entire M2P transfer atomically on the EN write; real silicon overlaps it with CPU work, so the async TIMING (CPU-does-work-while-stream-runs) is UNVERIFIABLE here. (2) TXE hardwired true in STM32F7_USART — no TX back-pressure modelled; a real UART would throttle the DMA via TXE/DMA-request handshake. (3) The DTCM->axiSram CPU stage-copy is an honest bridge, not zero-copy: codegen places the output array in DTCM (RAM), unreachable by real DMA1/DMA2, so dma_push copies it to the AXI-SRAM staging static first. A fully zero-copy real-DMA path would require codegen to place the output array directly in a DMA-reachable region (a larger codegen/linker change, filed as TASK-0048.13). (4) DMAMUX/peripheral-request wiring is irrelevant for TX (M2P fires on EN; the usart1->dmamux1 request line is PeripheralToMemory only) — carried from TASK-0048.11.

GOTCHAS / SUBTLETIES (forward-carry for future shim work):
1. LINKER (the big one): `INSERT AFTER .bss` is the WRONG anchor for an out-of-RAM-region NOLOAD static. cortex-m-rt link.x line 169-173 pushes __ebss to the end of any section inserted after .bss so it can be zeroed by startup; with the section at 0x2404_0000 (AXISRAM) and .bss at 0x2000_0000 (DTCM), startup's __sbss..__ebss zero loop walks the ENTIRE multi-MB DTCM->AXISRAM gap, hits 0x20020000 (end of 128K DTCM) immediately, faults silently, and the firmware never reaches dma_push -> 0-byte capture. FIX: `INSERT AFTER .uninit` (.uninit is NOLOAD + NOT zeroed; __euninit drives heap/stack placement which stays in RAM). Verified: NOBITS section @ 0x2404_0000, 0 OOB warnings, byte-exact. ANY future per-region static (e.g. SRAM1/2/3 buffers) must use the .uninit anchor, not .bss/.data.
2. NOLOAD really means no FLASH init: the staging static MUST be written before read (it is — the CPU stage-copy populates it each dma_push) since startup does not zero/copy it. Safe here; a future user adding a read-before-write static to .axisram_tx would read garbage.
3. STAGING CAP=4096 chosen as a safe upper bound over the largest M10 output (ex1/ex5 1024B). len>CAP is handled loud (usart1_puts diagnostic + early return), not silently truncated. If a future example streams >4096B per save, bump CAP or chunk the DMA.
4. The presence tests that previously asserted `usart1_putc(byte);` (skeleton/mod.rs + bin_shape x3) are now DMA1_S0CR/DMA_TX_STAGING assertions; usart1_putc itself stays alive (log/count sinks + usart1_puts), so no dead-code.

FORWARD-CARRY to TASK-0438.03 (M11 link-transport DMA hooks): the dma_link_arm / dma_link_recv_arm / dma_link_poll DEFAULT methods in NUCLEUS_SHIM_SRC (skeleton/mod.rs) carry the SAME real-engine hazard this task confronted on dma_push, PLUS the async-completion one .12 did NOT have to solve (because dma_wait is a sound no-op ONLY under Renode's synchronous-on-EN model). When a REAL async DMA engine backs the link transport: (a) the SOURCE buffer must be AXI-SRAM-resident (use the .axisram_tx / INSERT-AFTER-.uninit linker pattern proven here, NOT a DTCM static or `INSERT AFTER .bss`); (b) dma_link_poll MUST be overridden to read the silicon TCIF (DMA1 LISR/HISR bit for the stream), NOT the default `true` — otherwise the emitted `while !dma_link_poll(seq) { spin_loop() }` terminates on iter 0 and races the transfer, reading the buffer before the stream finishes and silently breaking byte-exactness. On Renode-with-synchronous-DMA both are masked (transfer done on EN, TCIF already set), so the race only bites on real silicon / a cycle-accurate model. This .12 dma_push deliberately AVOIDS the race by keeping dma_wait a no-op (sound under synchronous-on-EN); a real async link path cannot.

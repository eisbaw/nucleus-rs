## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Filed from the TASK-0048.11 de-risk SPIKE (commit f08fbcc), which empirically PROVED (Renode capture + negative control, both reviews GO) that Renode's stm32h743 model drives a real DMA1 MemoryToPeripheral USART1 TX end-to-end (tests/renode/dma-uart-smoke/ + just renode-dma-uart-smoke). This task would replace the embedded-pattern Usart1Shim::dma_push CPU-store loop (which currently reads a Renode-injected axiSram region and writes USART1 TDR via the CPU) with a real DMA-controller-driven push, mirroring the proven dma-uart-smoke register sequence (DMA1 stream PAR=USART1.TDR, M0AR=src, NDTR=len, DIR=MemToPeriph|MINC, EN; CR1=UE|TE load-bearing). FORWARD-CARRIED FINDINGS (TASK-0048.11): (1) STM32DMA fires MemToPeriph immediately on EN — no peripheral request wire / DMAMUX routing needed for TX (the usart1->dmamux1 line is absent in the .repl and irrelevant). (2) DmaEngine writes every byte to the FIXED TDR with PINC=0; CR3 DMAT is a no-op flag under Renode. (3) The DMA source buffer MUST live in a DMA-accessible region (axiSram/SRAM) NOT DTCM — on real H7 silicon DMA1/DMA2 cannot reach DTCM; Renode papers over this (models DTCM as plain MappedMemory). The current memory.x links output buffers in DTCM, so a real-DMA shim needs the output array relocated to a DMA-reachable region (a non-trivial codegen/linker change). EXPLICIT AC#1-RESCOPE DECISION (architect cycle review P2): parent TASK-0048 AC#1 literally says the shim 'provides DMA controller, IRQ bindings, memory layout'. The current synchronous shim provides none of a real DMA *controller* — it is a CPU store loop. We CONSCIOUSLY NARROW AC#1 for the M10 DoD: the synchronous shim is a sufficient HONEST M10 state because on a non-cycle-accurate emulator a real-DMA push yields the SAME captured bytes with no additional VERIFIABLE fidelity (Renode fires synchronously on EN; TXE hardwired true; no async overlap to validate). NUANCE: the DMA completion-IRQ EVENT (TCIF flag + UpdateInterrupt) IS modelled and DOES fire in STM32DMA.cs — so 'IRQ bindings' is partially testable; only the async TIMING is unverifiable here. This task is therefore a HW-faithfulness upgrade, deliberately LOW priority and NOT a blocker for closing M10.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
FORWARD-CARRY from TASK-0438.02 (landed 2026-06-05): the codegen seam for a real DMA engine now exists. NucleusShim gained 3 DEFAULT methods (NUCLEUS_SHIM_SRC in embedded-pattern/src/skeleton/mod.rs): dma_link_arm / dma_link_recv_arm (default delegate to link_push/link_recv) + dma_link_poll (default returns true = synchronous-completion model). A mode=dma transfer edge emits arm + `while !dma_link_poll(seq) { spin_loop() }`. To make this a REAL DMA1 MemoryToPeripheral USART1 TX, override these three on the concrete shim: dma_link_arm programs the DMA descriptor + starts the channel (non-blocking), dma_link_recv_arm arms the RX side, and dma_link_poll reads the real DMA transfer-complete flag (TCIF) — the generated spin loop then becomes a genuine completion-wait instead of a no-op single iteration. No codegen change needed in .12; it is purely a shim-impl override. Honest caveat carried from .02: today the bytes ride the SAME UART fabric via the link_* delegate (modelled DMA shape, not silicon DMA).

forward-carried from TASK-0438.03 (2026-06-05): the M11 DMA+PIO demo (22-dma-pio-demo) is now byte-exact under Renode with the MODELLED DMA — dma_link_arm delegates to link_push and dma_link_poll returns true synchronously, so the emitted `while !shim.dma_link_poll(seq) { spin_loop(); }` completion loop terminates on its FIRST iteration. When this task wires the REAL DMA1 MemoryToPeripheral USART1 TX engine, the link-transport DMA hooks (dma_link_arm / dma_link_recv_arm / dma_link_poll) have the SAME hazard as the dma_push path: dma_link_poll MUST be overridden to read the silicon transfer-complete / DMA-stream-status bit, NOT the default `true`. If left at the default, the spin loop races a real async transfer (reads the buffer before the stream finishes) and the byte-exact proof silently breaks. The demo currently proves VALUE-correctness only (parent TASK-0438 AC#4); a real engine here is what would let it also demonstrate timing (CPU does work while the stream runs).

## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## Background

Sparse Matrix-Vector multiply (SpMV) in CSR-style format: y[i] = sum_{k: row_ptr[i] <= k < row_ptr[i+1]} val[k] * x[col_idx[k]].

Filed under TASK-0341 (showcase example expansion).

## Why this example

SpMV is the classic data-dependent-indexing benchmark: x[col_idx[k]] is a load whose ADDRESS depends on runtime data (col_idx), not an affine expression of loop indices. This is the SAME compiler-feature class as TASK-0044.04 (histogram), which has data-dependent-WRITE addresses. SpMV provides a data-dependent-READ companion — together they cover both directions of the runtime-indexed access pattern.

## Honest scoping

For the SHOWCASE matrix's bit-identical-output requirement, real sparse formats are problematic:

- True CSR with variable nnz per row requires variable-size data structures (Vec<i32>, etc.) which the DSL doesn't yet handle (TASK-0012 aggregate-typed I/O is a known gap).
- The 'sparse' aspect is computationally trivial — only the indexing pattern matters for compiler exercise.

MITIGATION: store the sparse matrix in DENSE form (zeros materialized) but use the SPARSE INDEXING PATTERN (load col_idx[k] then x[col_idx[k]]). The compiler doesn't know the values are mostly zeros — it sees the data-dependent indirect load. This sidesteps the variable-nnz problem while preserving the compiler-exercise property.

Specifically: a 16x16 matrix with 4 nonzeros per row, stored as a fixed-stride i32[16][4] (val) + i32[16][4] (col_idx) + i32[16] (x) + i32[16] (y output). Total < 1KB of binary input, trivial to verify bit-identical.

## What this exercises in the compiler

- Data-dependent indirect read (x[col_idx[i][k]]).
- 2-level indexing: outer loop over rows i, inner loop over k in [0, 4).
- Reduction in the inner loop (y[i] = sum of products) — already covered by 03-reduction, but combined with the indirect read it's new structural territory.

## Predicted outcome

If the DSL can express 'load a[b[i][k]]' (read whose address is another loaded value), this lands cleanly with all four tier-1 backends. If it can't, the honest-BLOCKED outcome names the missing DSL primitive — same value as TASK-0341.02's gap-probe outcome.

The companion-to-08-histogram framing means cycle 178+ orchestrators can use whichever example surfaces first to drive the compiler-extension follow-up, with the other example becoming the regression-pin once the extension lands.

EXPRESSIBILITY VERDICT (AC#2, decided at plan time by grammar
inspection of docs/grammar-algo.md):

  IndexExpr ::= AddExpr
  AddExpr   ::= MulExpr (('+'|'-') MulExpr)*
  MulExpr   ::= UnaryExpr (('*'|'/'|'%') UnaryExpr)*
  UnaryExpr ::= ('-')? Atom
  Atom      ::= IntLit | Ident | '(' AddExpr ')'

`x[col_idx[i][k]]` is GRAMMATICALLY INEXPRESSIBLE in the v2 algorithm
sublanguage: an IndexExpr's Atom rule admits only IntLit / Ident /
parenthesised AddExpr. A nested IndexSuffix (`col_idx[i][k]`) inside
an IndexExpr (`x[...]`) is not in the grammar. AC#2 closes as honest-

DIMENSIONS:
- M    = 8  (rows)
- N    = 8  (columns of the dense input vector)
- NNZ  = 3  (nonzeros per row; fixed, dense-stored)
- input.bin layout (224 B total):
    [0   ..  96)  val[M][NNZ]    — M*NNZ i32 LE
    [96  .. 192)  col_idx[M][NNZ] — M*NNZ i32 LE
    [192 .. 224)  x[N]            — N i32 LE
- reference.bin: 32 B (y[M] LE)

Input pattern (deterministic, hand-rollable):
  val[i][k]     = (i + 1) * (k + 1)   # small positives
  col_idx[i][k] = (i + k) mod N       # wraps cleanly
  x[j]          = j + 1               # 1..N
Each y[i] = sum over k of val[i][k] * x[col_idx[i][k]]; for row 0
that is 1*1 + 2*2 + 3*3 = 14. The pattern varies in both i and k so
a transposed-loop bug shows.

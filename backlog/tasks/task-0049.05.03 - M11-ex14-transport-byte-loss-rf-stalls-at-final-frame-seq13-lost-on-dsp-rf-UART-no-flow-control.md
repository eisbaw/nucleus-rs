ROOT (logical): rf blocks forever on link_recv(seq1) frame 3. dsp PROVABLY sent seq1[3] (fe completed all 4 frames => dsp reached push4[3]=E[3], which is AFTER push1[3]=B[3]) yet rf never received it. No logical deadlock in the dependency graph (frame-0 trace drains clean; pipeline is satisfiable). So the seq1[3] bytes are LOST at the Renode UART byte-delivery layer -> hypothesis: RX OVERRUN / no flow-control on the unbuffered STM32F7_USART (consistent with TASK-0049.01's durable finding that UARTBase.WriteChar DROPS chars not yet read / not queued). link_push is non-blocking (poll TXE, write TDR); a multi-byte burst with no per-byte/per-frame back-pressure relies on the fine global quantum (0.00001) interleaving sender-write and receiver-read; frames 0-2 align by luck, frame 3 the timing drifts and a byte is overwritten before rf reads it -> rf under-reads and blocks. CANDIDATE FIXES (pick empirically next cycle): (a) per-transfer RX-ready handshake / ACK so the sender does not transmit frame f+1 until the receiver consumed frame f (real flow-control; this is .05.02 item-1 'cyclic RX-ready handshake' territory); (b) check Renode STM32F7_USART RX buffer model + raise BufferState/quantum so a 256B burst is not overrun; (c) make link_recv poll-ready BEFORE the matched link_push fires (rendezvous). VERIFY NEXT CYCLE: rfUart reaches 256B and combined 512B; then the renode-multimcu cmp reveals whether per-frame VALUES are right (they look right for frames 0-2, so TASK-0049.02 may already be satisfied). ## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
PLAN (boot-order route, not handshake):
1. Replace compute_boot_order (waits-DESC, worker_id-ASC sort) with a deterministic STAGED-RELEASE SIMULATION over the per-worker Event lists.
   Model: a worker is releasable when releasing it (and any already-released receive-gated workers it transitively unblocks) issues NO link_push targeting a not-yet-released peer. A link_recv blocks until its producer pushed; a receive-gated worker released early blocks harmlessly. Greedily pick the smallest-worker-id releasable worker each round (tie-break deterministic).
2. Derive the per-worker first-push-target + recv-dependency structure from Event::Push{dst,seq}/Event::Wait{src,seq} ONLY (no worker-name hardcoding). Reuse the existing flatten/loop-recursion shape.
3. If NO worker is releasable in a round (genuine mutual-eager-send cycle) FALL BACK to a deterministic order (worker_id ASC) + emit a loud doc comment that the static order may be unsound for a truly cyclic interconnect and reference the deferred RX-ready-handshake follow-up (.05.02 item-1). Never silently ship a possibly-wrong order.
4. Biting unit test (src/tests/boot_order.rs): ex14 analogue (dsp=recv-gated central; fe,rf eager senders; dsp pushes to rf before fe) asserts order releases dsp first and rf before fe; FAILS if worker_id-ASC tiebreak restored. Plus 02-split-add order unchanged.
5. Gate: build+clippy+test+test-release+e2e (427/364/0/63/0); renode-multimcu 02 byte-exact 1024B; renode-multimcu 14 rfUart->256B combined 512B byte-exact.
6. Keep general-cyclic RX-ready-handshake as documented follow-up.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
ORCHESTRATOR PRE-ANALYSIS + EMPIRICAL ROOT-CAUSE CONFIRMATION (2026-06-04, before implementer brief). The task's 'RX overrun / no flow-control / raise RX buffer' hypothesis is REFUTED. Static facts: (1) Renode UARTBase RX queue is an UNBOUNDED Queue<byte> (UARTBase.cs:138); RXNE=Count!=0; the ONLY drop path is WriteChar when !IsReceiveEnabled (receiver CR1 RE&&UE off). No overrun possible once RX is enabled. (2) Generated ex14 transfers are WHOLE-ARRAY (size_of_val(&whole 64-elem array)=256B), re-sent EVERY frame (4x256=1024B/channel, balanced). link_push non-blocking (TXE hardwired true); link_recv blocks for len bytes. (3) Generated .resc boot order = dsp, fe, rf (rf LAST), from compute_boot_order (waits_before_first_push DESC, worker_id ASC; fe & rf TIE at 0, worker_id puts fe<rf). ROOT CAUSE: dsp boots first (blocks on recv mic_in); fe boots 2nd, pushes mic_in -> dsp unblocks -> dsp link_push(1,bt_out) -> rf.usart2, but rf HAS NOT BOOTED so its RX is disabled -> all 256B of frame-0 bt_out DROPPED (the TASK-0049.01 WriteChar drop). rf boots last, blocks recv bt_out frame0; the whole-array resend means dsp's frame-1 send carries frame-0 data in [0..16], so rf reads it & transmits frame0 correctly but ONE FRAME BEHIND. Masks the drop for frames 0-2; rf's frame-3 recv needs a 5th dsp send that never comes -> rf blocks -> rfUart=192B. EMPIRICAL A/B (cross-compiled the 3 ex14 firmwares, hand-edited .resc only, Renode 5.0s window): ORIG dsp,fe,rf -> feUart=256B, rfUart=192B (reproduced, pacing ruled out at 5.0s); SWAP dsp,rf,fe -> feUart=256B, rfUart=256B (FIXED). So it is a BOOT-ORDER / start-gating defect: rf (a receiver of dsp's bt_out) must enable RX before fe triggers the dsp->rf cascade. ex14's worker interconnect is CYCLIC (dsp<->fe, dsp<->rf) so there is no universal static receivers-first order, BUT ex14 HAS a valid deterministic order (dsp,rf,fe). GOTCHA for a handshake fix: a naive RX-ready handshake has the SAME bootstrapping drop (the READY token dsp->rf on seq3 is dropped if rf's RX isn't up yet) -> would deadlock under boot order dsp,fe,rf; a robust handshake needs retransmit-until-acked. Fix options: (i) principled boot-order correction sufficient for ex14 (NOT a hardcoded 'rf before fe'; e.g. order net-source workers by the order their common central sender pushes to them) + honest cyclic-general limit kept as follow-up; (ii) full retransmitting RX-ready handshake (robust, more code). See memory project-ex14-transport-boot-order-rootcause.

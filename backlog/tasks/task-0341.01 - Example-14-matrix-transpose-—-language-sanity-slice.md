## Background

Matrix transpose: out[j][i] = in[i][j]. Pure permutation primitive — affine 2D indexing with axis-swap. Sits between 01-elementwise-add (1D unit-stride) and 07-matmul (full multiply with reduction) in the existing matrix.

Filed under TASK-0341 (showcase example expansion).

## Why this example

Exercises NON-TRIVIAL 2D access patterns that no existing example covers:

- The producer write is unit-stride in axis-0 of `out` (good cache locality).
- The consumer read is unit-stride in axis-0 of `in` (also good).
- BUT producer-write and consumer-read see DIFFERENT row-major linear orders — this is precisely the 'transpose pattern' that surfaces tile-tiling tradeoffs in real implementations.

For a 16x16 input on 4 workers with partition=rows on the OUTPUT, each worker writes 4 contiguous output rows. To populate those, each worker must READ 4 columns of input — a strided access pattern. This is the structural test partition_workers + partition_rows has NOT yet been exercised on (since 06/separable-filter has 2 sequential row-only passes, not a row-vs-column dependence).

## What's substantively new vs existing examples

- vs 01-elementwise-add: 2D instead of 1D; cross-axis access dependency.
- vs 07-matmul: NO reduction; pure permutation. Lighter weight to test scheduling primitives in isolation.
- vs 06-separable-filter: the cross-axis structure makes partition=rows on `out` REQUIRE strided read of `in` (where 06 has both passes row-aligned).

## What this exercises in the compiler

- partition_workers on the OUTPUT dimension where input has different layout.
- transfer_inject for cross-worker INPUT data fan-in (each output worker needs columns from every input worker).
- safe_push_reorder (cycle 162) — likely no impact; transpose has no Loop bodies with w2w Push.
- host_data_relay_inject (cycle 163) — also likely no impact; no in-Repeat-body w2w Push.

If this example lowers and runs bit-identically, it validates that the cycle-147-onward cross-worker transfer machinery handles the 'output-driven partition with strided input' case.

## Honest gotchas

- Determining bit-identical output across backends is trivial here (integer permutation; no FP).
- If the DSL can't express the partition=rows-on-output with cross-column-read pattern cleanly, the naive (single-worker) schedule still passes pthreads-sync, but the multi-worker schedules become follow-ups.

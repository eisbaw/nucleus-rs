## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Forward-carried from TASK-0048.04 (no_std monotonic clock for check_frame). TASK-0048.04 fully lowers on_violation=log (SysTick monotonic clock via NucleusShim::monotonic_ns + a per-violation UART line via NucleusShim::report_violation) and REJECTS on_violation=count + on_violation=panic with typed EmitErrors.

Two things deferred here:

1. on_violation=count tier-3 sink. The tier-1 count action increments a static AtomicU64 and prints a summary at a Drop-guard's main-return Drop. On bare-metal that does NOT work: (a) AtomicU64 is unavailable on thumbv7em (only 32-bit LDREX/STREX; would need AtomicU32), and (b) a firmware spins forever in loop {} so Rust Drops at main return NEVER fire (docs/check-loop-latency-max.md §3). A real tier-3 count needs a different sink: a periodic per-N-iteration UART summary, an in-flash counter dumped on watchdog reset, or an RTT channel. DECIDE the sink, then wire NucleusShim with a count method (or extend report_violation) and remove the Count rejection arm in embedded-pattern/src/lib.rs render_event Loop arm.

2. Separate diagnostic channel. Today report_violation writes the on_violation=log line over the SAME USART1 the firmware streams its raw output bytes over (e.g. ex1 save_output). The captured stream interleaves ASCII violation lines with raw output (distinguishable by the 'check loop ' prefix, but a real deployment wants them on separate channels — a 2nd UART / RTT).

Code anchors (all in nucleus/backends/embedded-pattern/src/): lib.rs render_event Loop arm ViolationKind::Count match arm; skeleton.rs NUCLEUS_SHIM_SRC report_violation + Usart1Shim::report_violation. Negative regression pins: tests.rs check_loop_count_is_rejected_with_followup_link.

### Count-sink design (carried forward from the TASK-0048.04 orchestrator review — acting on it):
- AtomicU32 not AtomicU64: AtomicU64 is UNAVAILABLE on thumbv7em-none-eabihf (only 32-bit LDREX/STREX). core::sync::atomic::AtomicU32 with Relaxed ordering (single-core firmware; counter only read after run() on the same core).
- No Drop-guard: firmware spins forever in loop{}, so Rust Drop at main-return never fires. THE SINK = emit the summary AFTER run(&mut shim) returns and BEFORE loop {} in the cortex-m-rt #[entry] — the bare-metal program-exit equivalent.
- Module-scope static per count check-loop: static NUC_CHECK_COUNT_<ident>: AtomicU32 = AtomicU32::new(0); emitted by BOTH render_lib (so the M9 lib compiles) AND render_bin_main (bin path). ident sanitized with the same sanitize rule the Log path uses (iter-var is a parsed identifier so it is already valid).
- Count arm in render_event (shared lib+bin, single site): mirror the Log arm's SysTick timing (shim.monotonic_ns before/after) but on violation emit NUC_CHECK_COUNT_<ident>.fetch_add(1, Relaxed) instead of report_violation.
- Summary line in render_bin_main (bin-only inline code): for each count check-loop, emit usart1_puts(b"check loop `<lv>` violated latency_max=<ns> ns: <count> occurrence(s)\n") with usart1_put_u64 reading NUC_CHECK_COUNT_<ident>.load(Relaxed). NO 7th trait method (counter is the shared seam; summary is bin-only inline).
- Collector: an embedded-local collect_count_check_loops walking the event list for Event::Loop whose check_frame.on_violation==Count (mirrors backend_common::check_frame::collect_count_check_frames in SHAPE but emits AtomicU32 not U64 and a different summary). ## Limits (honest)
- The count is Renode-specific 255 (not a structural 256). On real silicon iteration-0's body would advance >0 ns and the count would be 256; under Renode it is 255. The recipe band (255-256) covers both honestly.

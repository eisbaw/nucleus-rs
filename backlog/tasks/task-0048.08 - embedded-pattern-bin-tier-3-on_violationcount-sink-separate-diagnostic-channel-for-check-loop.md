TASK-0048.04 fully lowers on_violation=log (SysTick monotonic clock via NucleusShim::monotonic_ns + a per-violation UART line via NucleusShim::report_violation) and REJECTS on_violation=count + on_violation=panic with typed EmitErrors.

Two things deferred here:

1. on_violation=count tier-3 sink. The tier-1 count action increments a static AtomicU64 and prints a summary at a Drop-guard's main-return Drop. On bare-metal that does NOT work: (a) AtomicU64 is unavailable on thumbv7em (only 32-bit LDREX/STREX; would need AtomicU32), and (b) a firmware spins forever in loop {} so Rust Drops at main return NEVER fire (docs/check-loop-latency-max.md §3). A real tier-3 count needs a different sink: a periodic per-N-iteration UART summary, an in-flash counter dumped on watchdog reset, or an RTT channel. DECIDE the sink, then wire NucleusShim with a count method (or extend report_violation) and remove the Count rejection arm in embedded-pattern/src/lib.rs render_event Loop arm.

2. Separate diagnostic channel. Today report_violation writes the on_violation=log line over the SAME USART1 the firmware streams its raw output bytes over (e.g. ex1 save_output). The captured stream interleaves ASCII violation lines with raw output (distinguishable by the 'check loop ' prefix, but a real deployment wants them on separate channels — a 2nd UART / RTT).

Code anchors (all in nucleus/backends/embedded-pattern/src/): lib.rs render_event Loop arm ViolationKind::Count match arm; skeleton.rs NUCLEUS_SHIM_SRC report_violation + Usart1Shim::report_violation. Negative regression pins: tests.rs check_loop_count_is_rejected_with_followup_link.

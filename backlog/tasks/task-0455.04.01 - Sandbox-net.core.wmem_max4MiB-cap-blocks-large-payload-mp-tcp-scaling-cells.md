## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by TASK-0455.04 (runtime/scaling study). The mp-tcp-bufsync / mp-tcp-event backends setsockopt(SO_SNDBUF) to the largest per-channel transfer payload; when that exceeds this sandbox's net.core.wmem_max (4194304 B = 4 MiB, un-raisable here per memory env-netns-sysctl-limits) the host worker panics with a fail-loud diagnostic ('socket buffer too small: requested NUC_SO_BUF=N but the OS granted only 4194304') and the cell cannot RUN. The perf-study runner detects this deterministically and records CAPSKIP for the 6 affected cells (stencil >=7680x640 at w<=4 where the per-channel band exceeds 4MiB; reduction 2^24 whole-array scatter = 64MiB). This is an ENVIRONMENT wall, NOT a backend defect: the identical cell runs on a host whose wmem_max is raised (e.g. sysctl -w net.core.wmem_max=67108864). W-dependence is correct: stencil 7680x640 runs at w=8 (8-way band drops payload under cap) but CAPSKIPs at w=2/w=4. To lift HERE would need either CAP_SYS_ADMIN to raise the sysctl, or a backend change to chunk a transfer into <=cap-sized sends (which would change wire framing). Out of scope for the study; documented in docs/perf-study.md sec 6 wall 1.

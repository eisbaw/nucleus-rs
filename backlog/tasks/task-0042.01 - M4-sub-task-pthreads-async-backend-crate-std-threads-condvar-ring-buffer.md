## Forward-carried lesson from TASK-0134 (TASK-0042.01 implementer reads this)

TASK-0134 landed the IR contract for `pipeline=D` initial markings:

- `ACFG::pipeline_depth_for_seq: BTreeMap<SeqTag, NonZeroU64>` carries (Push/Wait pair seq -> head-start depth D).
- `acfg_to_petri` reads this and sets `Place::initial_marking = D` on the corresponding buffer place.
- The link step (`LinkError::PipelineExceedsBuffer`) rejects `D > buffer=N` at compile time, so by the time codegen runs, D <= N is guaranteed for every (seq, place) pair.

### Ring-buffer pre-fill contract

When the pthreads-async backend lands, the IR's initial-marking annotation IS the authoritative source of "how many head-start producer-pushes were notionally pre-fired". Concretely:

- Per (DataId, SeqTag) buffer ring of size N (= transfer's `buffer=N`),
- If `pipeline_depth_for_seq[seq] = D`, the ring must START with D pre-filled slots (or D slots reserved on the producer side — see "interpretation (a)" in TASK-0134 notes for the chosen semantic).
- Do NOT recompute D from the schedule at codegen time. The Petri net IS the authoritative encoding; the EventList contract (TASK-0124) should expose the per-seq initial marking so the backend can read it directly.

### EventList plumbing gap (file as a sibling sub-task if it bites)

The current `Event` enum (PRD §8.3) carries `seq: SeqTag` on Push/Wait events but does NOT carry the buffer place's initial marking. The backend either needs:
(a) a new event variant or annotation carrying the per-seq initial marking, OR
(b) access to the Petri net's `Place::initial_marking` via the codegen sidecar (TASK-0124 expanded).

Either way: do NOT derive D from the schedule at codegen — derive it from the IR (single source of truth).

### Boundedness/firing-order known issue (TASK-0213)

The boundedness pass currently does NOT pass on a `pipeline=D, buffer=D` net under source-order firing. TASK-0213 will land the marking-aware firing-order generation OR a structural acfg_to_petri rewrite (eliding D pre-fired Push transitions). The pthreads-async backend codegen should NOT depend on the boundedness pass passing; it should consume the per-seq initial marking directly. The boundedness pass is an analysis-time invariant check, not a codegen pre-condition.

## CORRECTION (forward-carried from TASK-0213 — supersedes prior "Ring-buffer pre-fill contract")

The TASK-0134 forward-carry note above CONTAINS A NOW-INCORRECT INSTRUCTION. It says the ring must "START with D pre-filled slots" / "D producer-pushes were notionally pre-fired". After TASK-0213 (commit 4b3e7ad) clarified the IR semantics, this is WRONG and would mislead this implementer into building a defect.

### Corrected ring-buffer contract (post-TASK-0213)

The IR's `initial_marking = D` on a buffer place is the ANALYSIS-ENCODING CARRIER of pipeline depth D. It is NOT a runtime pre-fill instruction. At runtime:

- Per (DataId, SeqTag) the ring is sized to `buffer = N` (the `transfer DATA : buffer=N` directive).
- The ring STARTS EMPTY.
- Producers push and consumers drain naturally; the ring holds at most D items concurrently because only D pipelined iterations are in flight.
- Pre-filling the ring with D tokens at thread spawn would be a DEFECT — the producer's first N real pushes would then deposit on top of an already-D-full ring and overflow at runtime (the IR's analysis net would still accept this, because acfg_to_petri elides the first D Push TtoP arcs as "head-start credit"; the runtime would actually crash).

### How to read D from the IR for this implementer

`D` is the pipeline depth, the SIZING input — not a fill input. Source path:
- IR carrier: `ACFG::pipeline_depth_for_seq: BTreeMap<SeqTag, NonZeroU64>`.
- Petri carrier: `Place::initial_marking = D` (analysis-only).
- EventList carrier: NOT YET WIRED. The current Event enum carries `seq: SeqTag` on Push/Wait but does NOT carry D. The pthreads-async backend needs ONE of:
  (a) a new Event annotation `Push { seq, depth, ... }` / `Wait { seq, depth, ... }`, OR
  (b) access via the codegen sidecar to `pipeline_depth_for_seq` (TASK-0124 EventList contract — extend to surface D), OR
  (c) the ring size `N` directly (which is `>= D` by link-step invariant), making D irrelevant for sizing.

Recommended: option (c) for sizing. Reading `buffer = N` is sufficient — the ring just needs to hold N items, empty at start, and behave like a bounded FIFO. D is the *behaviour invariant*, not a *sizing input*; once the ring is sized N, runtime correctness is structural.

### Why interpretation (a) of PRD §8.2 is still right

The boundedness/deadlock analyses need a way to express "the buffer has D credits in flight at steady state". Interpretation (a) puts D head-start tokens in the buffer place and elides the first D producer pushes — the analysis net's algebra balances (D initial + (N-D) real pushes - N waits = 0). This is the IR's contract with itself, not with the backend.

### Codegen ring-buffer pseudocode (for this implementer)

```rust
// pthreads-async ring per (DataId, SeqTag).
let N = events.buffer_size_for(seq); // from `transfer DATA : buffer=N`
let ring = std::sync::Mutex::new(VecDeque::with_capacity(N));
let not_empty = std::sync::Condvar::new();
let not_full  = std::sync::Condvar::new();

// On Push event: lock, wait on not_full while ring.len() == N, push, notify not_empty.
// On Wait event: lock, wait on not_empty while ring.is_empty(), pop, notify not_full.
// At thread spawn: ring is EMPTY. No pre-fill, ever.
```

The pthreads-async backend is bounded by N (the link step + boundedness analyses guarantee this). D appears nowhere in the runtime code path.

### Corrected codegen contract for pthreads-async (post-TASK-0052.04)

The two tier-1 backends share helpers in `nucleus/backends/pthreads-sync/src/lib.rs`:
- `pub fn sanitize_loop_var(loop_var: &str) -> String` — defensive ident sanitizer (grammar already enforces idents; helper is unreachable in practice but documented).
- `pub fn collect_count_check_frames(events: &[Event]) -> Vec<CountCheckLoop>` — walks the EventList and returns one `CountCheckLoop { ident, loop_var, threshold_ns }` per `check_frame` whose on_violation is `Count`. Deterministic walk order.
- `pub fn emit_count_reporter_struct(out: &mut String, count_frames: &[CountCheckLoop])` — emits the file-scope `NucCheckCountReporter` struct + `Drop` impl ONCE per file, gated on `!count_frames.is_empty()`.
- `pub struct CountCheckLoop` — `{ ident: String, loop_var: String, threshold_ns: u64 }`.

The pthreads-async backend should:

1. Import the helpers: `use pthreads_sync::{sanitize_loop_var, collect_count_check_frames, emit_count_reporter_struct, CountCheckLoop};` (already done in mp-tcp-bufsync; same pattern).

2. In the per-file generator (whatever the pthreads-async equivalent of `render_main_rs` is): call `collect_count_check_frames` once per file; if non-empty, emit the static AtomicU64 declarations + the reporter struct + per-loop guard locals in `fn main`. See pthreads-sync `render_main_rs` (lib.rs ~lines 511-562) for the canonical pattern.

3. In the `Event::Loop` arm rendering: when `check_frame` is `Some`, dispatch on `frame.on_violation`:
   - `ViolationKind::Panic` — emit `panic!(...)` (the existing TASK-0052.02 pattern).
   - `ViolationKind::Log` — emit `eprintln!("warning: check loop \`{lv}\` violated latency_max={ns} ns: iteration took {{}} ns", _check_elapsed)`. Execution continues. Stdout untouched. Cross-backend differential remains green.
   - `ViolationKind::Count` — emit `NUC_CHECK_COUNT_<sanitized_loop_var>.fetch_add(1, std::sync::atomic::Ordering::Relaxed)`. The file-scope static + Drop guard handles the run-end summary.

4. Forward-carry for multi-worker pthreads-async: until TASK-0052.05 lands, multi-worker `check_frame` should reject with `EmitError::ContractGap` (same as tier-1 sync backends do today in `multi_worker.rs`). The Log/Count helpers above are for the SINGLE-worker / per-worker-process path.

5. Ring-buffer + condvar codegen (the actual pthreads-async novelty): orthogonal to the check_frame codegen. The check_frame layer runs at the loop-boundary level (rolled `Event::Loop`); the ring-buffer + condvar layer runs at the Push/Wait level. They don't interact directly.

The pthreads-async backend will be the THIRD tier-1 backend (after pthreads-sync + mp-tcp-bufsync). The check_frame codegen pattern is now stable on the two existing backends; the implementer of pthreads-async should READ + REUSE rather than re-invent.

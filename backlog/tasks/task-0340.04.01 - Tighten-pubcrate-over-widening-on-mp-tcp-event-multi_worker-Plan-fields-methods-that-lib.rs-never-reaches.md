## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Plan (orchestrator-implemented in-thread; low-risk visibility hygiene, compiler-verified). KEY CORRECTION to the AC: tightening to pub(super) is a NO-OP for items in multi_worker/mod.rs — mod.rs is a direct child of the crate root, so pub(super) (visible to parent=crate root + its descendants) == pub(crate) in reach AND would still expose to lib.rs, FAILING the stated goal (items lib.rs never reaches). The correct tightening is PRIVATE: submodules encode/relay/walkers/worker_program are descendants of mod.rs and can access ancestor private items, while lib.rs (parent) loses access. Consumer audit (crate-wide grep): per_worker/names/sidecar/host_worker/chan_ids/chan_caps/chan_pairs/pair_tiles/accumulate_waits/barrier_participants (fields), data_name/non_host_workers/peer_index_for (methods), ChanId (type) are consumed ONLY by multi_worker descendants -> private. KEEP pub(crate): Plan, build, worker_name, used_workers (lib.rs reads), render_worker_program (worker_program.rs, called by lib.rs grandparent -> needs pub(crate)), render_run_sh (lib.rs calls). peer_index_for is already pub(super) (not pub(crate)) -> tighten to private too (same pattern). Compiler is the oracle; relax any item the build rejects. e2e AC number 112/102/0/10/0 is STALE -> verify against live baseline 308/246/0/62/0.

DURABLE LESSON (for any future per-backend Plan visibility-hygiene task): pub(super) on a module that is a DIRECT child of the crate root is NOT a tightening over pub(crate) -- super is the crate root, so reach is identical and it still exposes to the parent (lib.rs). For module-internal items consumed only by descendant submodules, the correct tightest level is PRIVATE (descendants see ancestor privates). An AC that prescribes pub(super) for such items is prescribing a no-op; verify the definition site depth before applying.

=== Cycle 212b correction (architect review-gate fold-back P1 — mechanism doc-lie) ===

The "What makes this LIKELY clean" bullet above claims:
- "17-spmv has NO in-Repeat-body w2w transfers (the inner k+j loops are NOT Event::Loop / NOT Repeat — they are straight nested for-loops)"

This is WRONG. 17-spmv's prog.algo.nuc:118-124 has three nested `for` loops, and nucleus-compiler/src/acfg/build.rs constructs ACFGNode::Repeat for EVERY IrStmt::For (event.rs:756 documents Event::Loop mirrors ACFGNode::Repeat one-for-one). So 17-spmv DOES have 3 nested Event::Loops in the emit.

Corrected mechanism: the TASK-0330 in-Loop w2w Push guard fires only on a w2w Push INSIDE an Event::Loop body. In 17-spmv, the w2w Push/Wait for val/col_idx/x/y all live at the TOP LEVEL of each worker's event list (visible as `w0_slot_*.wait()` calls BEFORE the `for i ...` line in /tmp/spmv-dist/src/main.rs), OUTSIDE the Loop nests; only Fire events live inside the Loops. 16-jacobi/distributed by contrast has w2w Pushes INSIDE the outer `for t : 0..ITERS+1` Repeat body, which is what trips the guard.

So the prediction "LIKELY clean" remains correct — every backend already PASSed empirically in cycle 212's e2e — but the mechanism is "no w2w Push inside an Event::Loop body" not "no Event::Loop at all".

See TASK-0341.03.02 final-summary cycle-212b addendum for the full lessons-learned writeup; this note is a narrower correction so the cross-backend promoter's onboarding doesn't inherit the wrong mechanism story.

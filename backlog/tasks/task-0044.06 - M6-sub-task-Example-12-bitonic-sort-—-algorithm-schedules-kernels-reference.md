## Goal

Land example 12 — bitonic sort — per PRD §9 row 12: 'Static communication pattern, fits SDF'. The first example with a DATA-DEPENDENT IN-PLACE sort using a fixed-shape communication pattern that fits the synchronous-dataflow (SDF) model — every stage knows in advance which element pairs to compare-exchange.

## What this stresses (per PRD §9)

- Algorithmic: bitonic sort network has a static compare-exchange pattern that depends only on input SIZE, not on input VALUES. Despite being a sort (data-dependent at the comparator level), the COMMUNICATION pattern is fully scheduled at compile time — making it a clean fit for SDF.
- Scheduling: naive (single worker, log²(N) stages) + parallel (N/2 workers per stage, each handles one compare-exchange pair). The PARALLEL schedule is the load-bearing test of static-but-irregular communication.
- 'Fits SDF' marker: this is the canary example for whether v2's schedule sublanguage can EXPRESS a stage-by-stage compare-exchange network. If it can't cleanly, that's a meaningful expressiveness boundary.

## Closest template

`nuc-nucleus/examples/02-split-add/` — the existing multi-worker compare/transfer example. Reuse:
- Multi-worker pattern with explicit data flow between worker pairs.
- input.bin / reference.bin oracle pattern.

The diff: bitonic sort is MULTI-STAGE — each of the log²(N) stages has a different pairing of elements. The naive schedule is a sequential loop over stages; the parallel schedule has all N/2 compare-exchanges within a stage in parallel, then barrier, then next stage.

## Honest scope

- Bitonic sort needs input length = 2^k. Pick a single fixed length (e.g. 1024) and document.
- Comparator MUST be total + deterministic. If input has duplicates, the comparator's tie-breaking determines the output bit-pattern. Use distinct integers for the canned input to sidestep the issue, OR document the tie-break rule.
- The PARALLEL schedule has N/2 workers — that's MANY workers for N=1024 (512 workers). The pthreads-sync backend may have a thread-count limit; consider a smaller N for the test (e.g. 16 elements, 8 workers max) or use a coarser worker assignment (e.g. 4 workers each handling N/8 pairs per stage).
- The stage-by-stage barrier may exercise existing sync_inject machinery in a new way; expect to discover whether the schedule grammar can express 'log²(N) stages of varying parallelism' cleanly, or whether it needs unrolling.

## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
EMPIRICAL FINDING from TASK-0049.10.04 (slice C1): the per-worker input.bin partition offset CANNOT be computed correctly from the codegen contract today. The reference generator (nuc-nucleus/examples/14-hearing-aid/reference/src/main.rs:74-87) writes input.bin in DATA-DECLARATION order: mic block (mic_in) first, then bt block (bt_in). But DataId is assigned ALPHABETICALLY (acfg/build.rs:60-66 enumerates linked.algo.data.keys(), and algo.data is a BTreeMap<String,_> keyed by name), so for ex14 bt_in=DataId(0), bt_out=1, mic_in=2, mixed=3, spk_out=4. Sorting loaded symbols by DataId therefore yields bt_in BEFORE mic_in => fe(mic_in)=offset 256, rf(bt_in)=offset 0 -- the REVERSE of the reference input.bin layout (mic at 0, bt at 256). So slice C1 Mechanism A (DataId-order concatenation) is UNSOUND for any schedule where >1 worker loads input (cross-worker input partition). Declaration order is LOST at AlgoIR construction (AST->IR stores data into BTreeMap<String,ResolvedData>) and is NOT present in NameSidecar (data_types: BTreeMap<DataId,ResolvedType>) or NameTables (data: BTreeMap<DataId,String>). ROOT FIX: preserve data-declaration order as a Vec<DataId> (or Vec<String>) through AST->IR->ACFG->NameSidecar so the embedded backend can build the global input.bin layout in the SAME order the reference generator hand-writes it. Then multimcu::compute_input_offsets sorts loaded symbols by that declaration-order index instead of DataId. SCOPE: compiler-layer (nucleus-compiler AlgoIR + ACFG + sidecar) + backend consume. SLICE C1 DISPOSITION (TASK-0049.10.04): classification fix landed (fe AND rf recognized as loaders, both get $input -- AC#1 done); single-loader offset 0 landed + 02-split-add regression-safe; the CROSS-WORKER multi-loader offset FAILS LOUD (EmitError) referencing THIS task rather than emitting a byte-wrong offset. AC#2 (fe=0/rf=256 emit) is BLOCKED on this task.

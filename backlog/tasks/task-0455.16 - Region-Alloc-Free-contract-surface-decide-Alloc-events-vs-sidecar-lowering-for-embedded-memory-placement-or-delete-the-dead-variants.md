DECISION RATIONALE (recorded before implementing, AC#1):

Three options weighed:
(a) Make Alloc-events load-bearing (projection emits, embedded consumes). REJECTED-FOR-NOW: no accepted schedule needs them; synthesising first-use=Alloc/last-use=Free would be guessing semantics no consumer relies on (the petri_to_events skip rationale, still true). The thesis explicitly frames Alloc/Free as the hook a FUTURE GPU tier would make load-bearing, not the embedded tier.
(b) Sidecar place_data region fact (XferFacts precedent). REJECTED-FOR-NOW: the ONLY 4 place_data directives in the whole example corpus live in 14-hearing-aid/embedded_multimcu.sched.nuc, which the embedded backend correctly REJECTS at check_schedule_compat (it requests region sram_shared; embedded capabilities.toml declares only heap). The gated schedule embedded_multimcu_sync.sched.nuc deliberately has NO place_data. So there is ZERO accepted producer of region placement. A sidecar consumer would be speculative machinery for an input no shipping/accepted schedule emits — the opacity-gate-rot + bottom-up discipline says do not build the consumer before a real producer exists. (When TASK-0455.13 banded-receive + real TCM placement lands an ACCEPTED place_data, the sidecar is the right route then — recorded as the forward path.)
(c) Delete Alloc/Free/Region. REJECTED: blocked by paper/chapters/06-architecture.tex (sec:arch-petri: contract reserves Alloc/Free) + 11-future-work.tex:182-184 (sec:fw-tiers: Alloc/Free reserved, would become load-bearing for a GPU tier) + figures/petri.tex. paper/ is owned by another agent this wave; deleting the variants would falsify a live, load-bearing thesis claim.

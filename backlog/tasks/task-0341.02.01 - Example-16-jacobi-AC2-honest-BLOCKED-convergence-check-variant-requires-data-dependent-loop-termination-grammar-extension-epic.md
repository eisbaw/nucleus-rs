## HONEST-BLOCKED rationale

Data-dependent loop termination is structurally inexpressible in Nuc's algorithm sublanguage today. Per `docs/grammar-algo.md` §1:

  ForStmt ::= 'for' Ident ':' ConstExpr '..' ConstExpr '{' Stmt* '}' ;

Loop bounds are `ConstExpr` (compile-time const expressions) — not runtime values. There is no `while`, no `if`, no `break`. The grammar does NOT covers:
- Loop bound that depends on a runtime-computed reduction.
- Conditional branch on a reduction result.
- Early-exit / break out of an iteration.

The fixed-iteration variant (cycle 206) IS what is expressible today; the convergence variant requires a grammar extension.

## Scope (when this task becomes actionable)

A grammar extension covering "loop until condition" needs to address several axes simultaneously:

1. **Grammar**: a new statement form `while CONDITION_EXPR { Stmt* }` or `for IDENT : RUNTIME_BOUND { ... }` (where RUNTIME_BOUND can reference reductions).
2. **Lowering**: AlgoIR currently encodes for-loops as a Repeat node with const bounds; runtime termination needs a different IR shape — likely a fixed-point iteration node carrying the termination predicate.
3. **ACFG / Event**: how does a runtime-terminating loop project into the Petri net? Each generation reads from the previous one, so the cross-iteration edge is well-defined; the termination condition is a separate read-then-control-flow edge that the current Petri encoding doesn't have a place for.
4. **Scheduling**: pipelined / multi-worker schedules over a runtime-terminated loop need a barrier on the termination check.
5. **Bit-identical determinism**: a runtime termination condition that depends on a reduction (max-abs-diff) is order-of-summation sensitive — would need integer fixed-point + a careful reduction tree to keep bit-identity across schedules.

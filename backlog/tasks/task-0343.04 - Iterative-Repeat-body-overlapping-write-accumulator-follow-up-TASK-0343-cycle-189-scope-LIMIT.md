## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-0343 cycle 189 only detects the top-level overlapping-write fan-in (08-histogram/distributed shape: 4 workers push whole-array partials once, host receives N>=2 whole-array Waits at the root sequence).

Iterative / multi-pass accumulator patterns are out of scope: Waits inside an Event::Loop body carry per-iter tiles (the enclosing iter-var range is one of the consulted dims), so they do NOT match the whole-array predicate and the cycle-189 helper does not classify them. A future multi-pass time-step accumulator (e.g. an iterative reduction over time-steps where each step contributes element-wise into a shared accumulator) would surface as a separate codegen-layer gap.

Filed at cycle 189 to be planned for when such a schedule lands in the e2e matrix.

Cross-references:
- TASK-0343 (parent): the cycle-189 top-level landing.
- backend-common/src/multi_worker_walker/collect.rs::collect_accumulate_waits LIMITS docstring section 'No iterative (Repeat-body) accumulator'.

## Implementation Notes

Forward-carried from TASK-0343.03 (algorithm-level accumulator cross-check, Done this cycle): two facts that bear directly on iterative (Repeat-body) accumulator support. (1) A new fail-loud gate now exists: backend_common::multi_worker_walker::check_accumulator_consistency (collect.rs), wired in driver/main.rs before codegen dispatch. It cross-checks each structurally-detected accumulate DataId against the algorithm-IR LHS-appears-in-RHS shape. When you add iterative-accumulator support, an in-loop accumulator may have a DIFFERENT algorithm shape (the LHS-in-RHS test is currently exact, non-transitive — see TASK-0343.03.02); make sure a legitimate iterative accumulator is recognised by collect_accumulator_names (in collect.rs) or it will be FALSE-REJECTED (fail-loud, not silent). (2) The structural detector collect_accumulate_waits CURRENTLY FILTERS OUT in-loop Waits via the whole-array predicate (walk_waits descends Loop bodies but in-loop tiles are typically not whole-array). So iterative/Repeat-body accumulators are NOT detected as accumulate today; enabling them means both the detector AND the cross-check (collect_accumulator_names) must co-evolve. ARCHITECTURE PATTERN (reusable): codegen-layer detectors in backend-common are contract-isolated from the AlgoIR; to validate a codegen detection against algorithm semantics, put the cross-check in backend-common (it sees both the detector and nucleus_compiler IR types; nucleus-compiler cannot depend back) and wire it ONCE at the driver pre-codegen dispatch — do NOT extend the NameSidecar wire contract.

Forward-carried lesson from TASK-0364 (cycle 222, commit 534eec4) — relevant because iterative (Repeat-body) accumulators also reason about in-loop Waits:

TASK-0364 added backend_common::multi_worker_walker::collect::check_let_at_wait_scope_safety — a fail-loud guard at render_worker_events entry that rejects (EmitError::ContractGap) any let-at-wait datum whose in-loop Wait is consumed at an ENCLOSING scope the Wait does not lexically dominate (would emit `let <name>` out of scope -> rustc E0425). It uses a lexical scope-path = stack of per-occurrence loop identities (fresh pre-order counter, NOT iter_var, because strip-mining reuses iter_var). Non-strict prefix = domination; root [] dominates all.

IMPLICATION for this task: when you add iterative-accumulator codegen that places a Wait inside a Repeat/Loop body, be aware that (a) the let-at-wait classifier descends into Loop bodies and WILL classify a whole-array in-loop Wait as let-at-wait unless the data is accumulate-fan-in or indexed-Fire-written (both excluded), and (b) the TASK-0364 guard now fires if such an in-loop let-at-wait Wait has a consumer at an outer scope. If your iterative-accumulator shape legitimately needs an in-loop Wait whose result is consumed outside the loop, you must EITHER keep the data out of the let_at_wait set (so the outer-scope `let mut <name>` pre-init is retained and the in-loop Wait emits a plain `name = rhs;`) OR co-locate the consumer inside the loop body. Do not silence the guard — it is the panic-not-diagnostic protection against a latent E0425 miscompile. The accumulate path itself is already excluded from let-at-wait (collect_let_at_wait_data skips accumulate_data), so a pure accumulator Wait will NOT hit the guard; the risk is a NON-accumulate companion datum in the same Repeat body.

=== Cross-link from cycle 212 (TASK-0341.02.02.01.02/.03 16-jacobi finding) — READ BEFORE extending the Repeat-body classifier ===

16-jacobi/distributed IS a schedule of the kind this task anticipated ("when such a schedule lands"): cross-worker field Waits live INSIDE an Event::Loop (the for t body), which the cycle-189 whole-array predicate does not classify. BUT cycle 212 proved 16-jacobi is NOT the element-wise iterative ACCUMULATE this task describes. Distinction a future implementer MUST preserve:

- THIS task (0343.04): a genuine iterative reduction where each time-step ADDS element-wise into a shared accumulator (acc[i] += contribution across steps). No in-tree schedule exercises it yet.
- TASK-0341.02.02.01.03 (16-jacobi): field[t] is SINGLE-ASSIGNMENT per (t,y,x); each worker OVERWRITES its band of field[t]; the cross-worker exchange reassembles field[t] by COPYING disjoint bands. This needs band slice-paste COPY, NOT accumulate. Mis-classifying it as accumulate is exactly the xN double-count bug empirically proven in cycle 212 (output == 4x reference).

So when collect_accumulate_waits is extended to reach Repeat-body Waits, it MUST discriminate (a) iterative element-wise accumulate [this task] from (b) cumulative cross-iteration partition-band COPY [.03]. The discriminator .03 proposes (data READ across an outer Repeat = cumulative => copy; written-once-disjoint = accumulate) is the same machinery both tasks need. Coordinate the two when either is picked up.

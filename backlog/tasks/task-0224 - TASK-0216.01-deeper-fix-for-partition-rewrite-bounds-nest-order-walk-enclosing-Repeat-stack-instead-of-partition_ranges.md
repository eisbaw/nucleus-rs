## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-0216 left this as a scope-split: the architect's id-order != nest-order concern is latent today (single-partitioned-iter-var schedules give a 1-element bounds vec), but a future schedule with multiple nested partitioned iter-vars under different IterVar ids could violate IterTile::bounds outer-to-inner convention. The proper fix is to rewrite rewrite_partition_tiles_inner to walk the enclosing Repeat stack instead of iterating partition_ranges (which gives BTreeMap key-ascending = IterVar-id ascending = nest-order-coincidence, not nest-order-by-construction). The current code is documented at the call site (transfer_inject.rs) explaining the assumption + risk.

## Cycle 78 — landed (commit 992a2d4)

Test-first approach (cycle-45 lesson) confirmed the latent gap: 2-level and 3-level synthetic fixtures with non-monotonic IterVar ids failed against the BTreeMap-key-order iteration. Refactor landed; both new tests + the load-bearing transfer_fanout_composes_with_partition_sidecar all green.

Design pivot from the task plan: instead of walking the live enclosing-Repeat stack at each Xfer (which fails for hoisted Waits — exactly the cycle-45 failure mode reproducing on first attempt), the refactor precomputes the program-wide partition-axis nest order via a single DFS pre-order over Repeat::iter_var, and iterates THAT vec at every Xfer. Derives nest order from ACFG topology rather than IterVar-id coincidence, while preserving the per-worker slice substitution semantic regardless of where any Xfer has been hoisted to.

Three existing synthetic tests had to be repaired — they had constructed an invariant-violating ACFG (partition_worker_ranges entry for an IterVar that had no matching Repeat node in the tree). The pre-TASK-0224 BTreeMap-iteration path silently accepted that invariant violation; the new topology-driven path correctly requires the Repeat to be present. Tests now construct the Repeat properly, mirroring what the partition_workers pass would have produced for a real schedule.

### Honest limits
The DFS-over-ACFG approach assumes any IterVar appearing in partition_worker_ranges also has a corresponding Repeat node in the tree. The partition_workers pass enforces this in real flows (its 'to_record' tuples come from discovered Repeats). If a future pass directly inserts a sidecar entry without a Repeat (the pre-fix synthetic-test invariant violation), that entry will be silently dropped from the bounds vec. This is the correct semantic — bounds without a backing iter-var is meaningless — but is a subtle contract change relative to the BTreeMap-iteration code.

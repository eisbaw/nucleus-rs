## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-0216 left this as a scope-split: the architect's id-order != nest-order concern is latent today (single-partitioned-iter-var schedules give a 1-element bounds vec), but a future schedule with multiple nested partitioned iter-vars under different IterVar ids could violate IterTile::bounds outer-to-inner convention. The proper fix is to rewrite rewrite_partition_tiles_inner to walk the enclosing Repeat stack instead of iterating partition_ranges (which gives BTreeMap key-ascending = IterVar-id ascending = nest-order-coincidence, not nest-order-by-construction). The current code is documented at the call site (transfer_inject.rs) explaining the assumption + risk.

## Context

TASK-0044.02.02 cycle 195 landed mp-tcp-poll multi-worker codegen by COPYING mp-tcp-bufsync's `src/{encode.rs, walkers.rs, plan/{mod.rs, events.rs, relay.rs, worker_program.rs}}` substrate verbatim and swapping the wait primitive (`wire::*_poll` vs blocking, `apply_nonblocking` setup line). Same precedent as the original backend-common lift (TASK-0244) — fail-fast prove a second consumer, then lift.

The two backends now have ~1700 LoC of duplicated plan/walkers/encode logic. The poll/bufsync difference lives EXCLUSIVELY in the emit layer:

- wait-primitive call-site swap (3 sites in events.rs + 1 in relay.rs)
- apply_nonblocking line after apply_sock_buf in worker_program.rs
- module-doc / banner-text provenance lines

Everything else (host election, xfer registry, slice-paste tile derivation, accumulator classification, FIFO-shape hazards including TASK-0330 / TASK-0332 guards) is identical.

## Scope

Lift the shared substrate to a new `nucleus/backend-common/src/tcp_plan/` (or sibling crate `nucleus/mp-tcp-plan/`) parameterised over a small trait:

```rust
trait WirePrimitives {
    fn read_msg_expect_call(cv: &str, seq: u64) -> String;
    fn write_msg_call(cv: &str, seq: u64, enc: &str) -> String;
    fn barrier_cross_call(cv: &str, bid: u64) -> String;
    fn sock_setup_extra(sock: &str) -> Option<String>; // apply_nonblocking line
    const BACKEND_NAME: &'static str;
    const TASK_TAG: &'static str; // for provenance lines
}
```

mp-tcp-bufsync impl returns `wire::read_msg_expect(&mut {cv}, {seq})` etc; mp-tcp-poll impl returns `wire::read_msg_expect_poll(&mut {cv}, {seq})` and `Some("wire::apply_nonblocking(&{sock});")`.

## Acceptance criteria

1. Both backends' plan/walkers/encode source surface collapses to a thin shim over the lifted code.
2. Every test that pins bufsync emit-string shape still passes.
3. Every test that pins poll emit-string shape (cycle-195 multi_worker_emit + pingpong) still passes.
4. e2e baseline unchanged (210/169/0/41/0 going into the lift cycle; SAME after).
5. byte-identical-vs-bufsync emit test (poll's tests/multi_worker_emit.rs canonicalisation) survives — the lift must preserve byte-identicality MODULO the same legal swaps that test already discharges.

## Risk + safety profile

- The duplication is bounded by the byte-identical canonicalisation test in poll's tests/multi_worker_emit.rs — any future drift between the two substrates surfaces there before it hits e2e.
- The lift is OPTIONAL pending a third consumer (e.g. mp-uds-bufsync or a future blocking-UDS sibling). Two consumers prove the abstraction is well-shaped; three consumers prove it's load-bearing.

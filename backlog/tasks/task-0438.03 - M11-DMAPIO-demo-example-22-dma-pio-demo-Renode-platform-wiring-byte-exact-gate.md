FORWARD-CARRY from TASK-0438.02 (landed 2026-06-05, commits bb3a702 + b0689e3): the embedded-pattern backend now emits divergent transport codegen. A schedule transfer edge with mode=dma renders shim.dma_link_arm(seq,...) (or dma_link_recv_arm for the Wait side) + a completion SPIN loop (while !shim.dma_link_poll(seq) { core::hint::spin_loop(); }); mode=pio (or absent) renders the unchanged shim.link_push/link_recv. So a 22-dma-pio-demo with ONE dma edge + ONE pio edge will visibly diverge in the emitted firmware. The 3 NucleusShim hooks are DEFAULT methods delegating to link_push/link_recv (dma_link_poll=>true), so the existing MultiMcuShim/Usart1Shim move the DMA bytes correctly over the SAME UART with NO override — i.e. the demo should be Renode byte-exact-capable without writing a new shim, because the modelled DMA shape rides the existing transport. GOTCHA for .03: the spin loop terminates immediately ONLY because dma_link_poll returns true synchronously; if .03/.12 ever wires a REAL async DMA engine, dma_link_poll must be overridden to read the silicon transfer-complete bit (else the spin still terminates early on the default true and races the real transfer).

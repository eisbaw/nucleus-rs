The defect is the seq->USART multiplexing in the generated MultiMcuShim (mmcu_link_base): MULTIPLE distinct transport seqs share ONE byte-FIFO USART with NO per-seq framing/demux, AND push/recv order diverges across the pair. Concretely on the dsp<->fe hub (usart2 both sides): fe pushes seq2 THEN seq0 per frame; dsp does recv(seq0) THEN recv(seq2). link_recv(seq,...) just reads the next N bytes off the raw UART FIFO regardless of seq, so dsp recv(seq0) consumes the bytes fe sent for seq2 and vice-versa; the framing desynchronises and drifts each frame until rf starves at frame 3. All arrays are [i32;64]=256B so this is NOT a size mismatch (the existing TASK-0049.05.02 framing) — it is a seq-multiplex + push/recv-order-agreement defect on a shared FIFO link. The dsp<->rf hub similarly carries seq1 (dsp->rf) and seq3 (rf->dsp) bidirectionally on one hub.

This is firmware-transport correctness (render_multimcu_main_rs / mmcu_link_base / TransportPlan hub assignment), NOT the slice-D recipe.

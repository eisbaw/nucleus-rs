## Goal

Land the sixth tier-1 backend crate `nucleus/backends/mp-tcp-poll`: workers are OS processes, transport is TCP loopback, notify is nonblocking poll, no buffer (sync, single-frame in flight). PRD §7.1 row 5.

This is a SYNC-side sibling of mp-tcp-bufsync: same multi-process + TCP-loopback substrate, but where mp-tcp-bufsync uses BLOCKING recv to wait, mp-tcp-poll uses NONBLOCKING I/O + a busy/yield poll loop. Capability-wise they look identical (both reject async/buffer/event); the SHIPPED RUNTIME differs only in the wait primitive. This matters for the milestone story: it demonstrates the capability matrix is genuinely orthogonal — same sync capability surface, two different I/O strategies.

## Closest template

`nucleus/backends/mp-tcp-bufsync` is the structural template:
- Same multi-binary output (per-worker bins + wire.rs + run.sh).
- Same `nucleus/mp-tcp-common` consumer (wire framing, port-picker, socket-option setting).
- Same emit() signature returning the per-worker bin list.

The diff is the wait primitive: where bufsync calls `wire::read_msg_expect()` blocking, mp-tcp-poll calls a nonblocking read in a `loop { match read { WouldBlock => std::thread::yield_now(), ... } }` loop. The wire framing + port-picker + run.sh + SO_*BUF setup all unchanged.

## Honest scope

- `nucleus/mp-tcp-common` already provides wire framing + port picker + SO_*BUF logic; ensure mp-tcp-poll consumes it cleanly without per-backend forking.
- The 'poll' notify variant is new in the capability schema. **Precursor: TASK-0044.02.01** lands the schema-validator widening BEFORE this task; the dependency edge is recorded on the tracker. If TASK-0044.02.01 reveals the validator does NOT hard-code the notify list (i.e. accepts any string), the precursor becomes docs-only and unblocks this task immediately.
- Hazard: a nonblocking-read loop that NEVER sees data (peer never sends) becomes a spin-deadlock with no error. Make sure the read loop has a bounded retry count or a deadline-driven timeout (project memory project-mp-tcp-event-vs-bufsync-safety-profile is the analog warning for the async sibling — sync poll has a similar mask-failure-modes hazard).
- run.sh: same shape as bufsync (host first, then non-host workers, propagate exit).

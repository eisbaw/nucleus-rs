## Goal

Land the multi-worker arm of openmp-rs: a rayon-scope (or rayon::join / par_iter) per-worker substrate with a barrier-style rendezvous mechanism replacing pthreads-sync's std::thread + Condvar. Capability surface unchanged (sync + shared-memory + barrier/blocking) so every multi-worker schedule that pthreads-sync handles MUST emit bit-identical output under openmp-rs.

This unblocks all multi-worker [[skip]] cells filed in TASK-0044.01 cycle 191:
- 02-split-add/split, 03-reduction/distributed, 06-separable-filter/distributed + distributed2, 07-matmul/distributed + distributed-2d, 08-histogram/distributed, 13-cnn-inference/batch_parallel

Each promotes to [[required]] once bit-identical is verified.

## Closest template

The same template TASK-0044.01 cycle 191 used for single-worker — pthreads-sync — but the multi-worker arm now: `pthreads-sync/src/multi_worker.rs` (684 LoC). The diff is the runtime substrate:

- pthreads-sync: `std::thread::spawn` + `std::sync::Condvar` for per-(DataId,SeqTag) rendezvous slots.
- openmp-rs: rayon `scope` (or `join` / `par_iter`) for the worker substrate; barrier-style rendezvous (rayon's implicit join at scope-end or a shared `std::sync::Barrier`).

Check whether `backend_common::multi_worker_walker`'s rendezvous_prefix mechanism extends to rayon, or whether a new arm is needed. Per project memory `project-backend-common-crate`, the lift surface is the single source of truth; do NOT fork the walker.

## Forward-carried lessons from TASK-0044.02.02 cycle 195 (mp-tcp-poll multi-worker)

When implementing openmp-rs multi-worker codegen, note:

1. **lower_for_test does NOT apply host_mediation_inject**. If your test fixture has a host-excluding barrier (e.g. 03-reduction/distributed places all work on w0..w3 with NO host), the backend's defensive ContractGap fires at `Plan::build` time. Fix: either route through the driver in the test, or apply `apply_host_mediation_inject` inline AFTER `inject_syncs` + `inject_transfers` and BEFORE `acfg_to_events`. See poll's `tests/multi_worker_emit.rs::separable_filter_06_distributed2_poll_equiv_bufsync` for the manual-pass-sequence template (mirrors bufsync's `tests/host_relay_emit.rs`).

2. **host_mediation_inject docstring driver gate enumeration**. The pass's pub-fn docstring at `nucleus/nucleus-compiler/src/passes/host_mediation_inject.rs` ENUMERATES backends that must apply it (cycle 195 widened to include mp-tcp-poll). When openmp-rs lands multi-worker, audit whether it needs this pass too — openmp-rs uses shared-memory barriers (std::sync::Barrier on Arc) so it likely does NOT need host mediation, but verify and update the docstring enumeration in lockstep.

3. **Sibling-of-bufsync emit-string oracle test pattern** is high-value: take the same input, emit through both your backend AND a 'twin' (here mp-tcp-bufsync) that should produce the same shape modulo a known swap-set, and assert canonicalised equality. Catches silent-sibling regressions of the swap before they hit `cargo build`. See poll's `tests/multi_worker_emit.rs` for the canonicalisation pattern (4 legal differences: wait-primitive call swap × 3 + apply_nonblocking line + module-doc/banner text).

4. **The cheap-subset gate IS load-bearing**. Cycle 195 baseline: 210/161/0/49/0 → 210/169/0/41/0 (+8 promoted). Run `just build && just clippy && just test && just test-release && just e2e` before EVERY commit. 3 e2e samples for non-flake.

5. **mp-tcp-common is the single source of wire helpers** — new wait-primitive variants belong THERE (cycle 195 added `read_msg_expect_poll`, `write_msg_poll`, `barrier_cross_poll`, `apply_nonblocking` to `wire_runtime.rs` with unit tests in `mp-tcp-common/src/lib.rs::tests`). openmp-rs likely won't have a wire layer (shared memory), but if it ever grows IPC primitives the same pattern applies.

## Cycle 195b orchestrator fold-back lessons (forward-carried)

Cycle 195 mp-tcp-poll multi-worker landed → cycle 195b fold-back caught 3 P1s + several P2s the implementer self-reported as clean. **Read these before starting**:

1. **`just clippy` clean-claim must be re-verified empirically** — cycle 194 + cycle 195 both shipped clippy regressions the implementer claimed clean. doc_lazy_continuation on multi-line `///` blocks (especially when one line starts with `+` or `-` after a list-marker-looking character) is the recurring trigger. Run `nix develop --command bash -c 'just clippy'` AFTER every edit that touches a docstring, not just at the end.

2. **Gate-enumeration drift across N doc sites is a silent-sibling defect** (cycle 195b architect P1.1, see feedback-silent-sibling-defect.md 15th firing). If you widen the driver gate (`apply_host_mediation_inject` / `apply_host_data_relay_inject` / `apply_safe_push_reorder`) to include openmp-rs, grep the SAME backend tuple across the touched file AND `nucleus/nucleus-compiler/src/passes/host_mediation_inject.rs` (3 enumeration sites at lines ~5, ~66-67, ~275-276 cycle-195b stamp). Each enumeration of the backend set is a candidate for widening.

   For openmp-rs specifically: rayon::scope is shared-memory; host-excluding barriers can use std::sync::Barrier::new(N) directly. `apply_host_mediation_inject` likely should NOT be applied to openmp-rs (it's a TCP-star topology fix). VERIFY this by checking pthreads-sync / pthreads-async — they don't apply it (they use std::sync::Barrier). If true, openmp-rs follows that path; the gate stays {bufsync, event, poll}.

3. **Env-var race in tests** — if your multi-worker tests touch any process-wide env, serialise them with a static Mutex (cycle 195b architect P2.1 pattern, see `nucleus/mp-tcp-common/src/lib.rs::POLL_ENV_SERIAL`). Edition is 2021, so set_var is NOT unsafe — don't add unsafe blocks defensively.

4. **Oracle test canonicaliser regression-bite** — if you write a byte-equivalence test that canonicalises one direction (e.g. `s/X/Y/g`), assert that the input ACTUALLY CONTAINS X before canonicalising. Otherwise the canonicaliser silently no-ops on a regression and the test passes while the code is wrong (cycle 195b QA P2.1 pattern).

5. **Doc-lie on per-call vs cached state** — cycle 195 wire_runtime.rs claimed "read ONCE per process" but read per-call. Verify any "once per process" / "cached" claim against the code that actually reads the value (cycle 195b architect P1.2).

6. **e2e flake tolerance** — 1/5 e2e samples flaked at cycle 195b with unidentified required-fail (full retained-scratch tree, no per-cell FAIL marker). On loopback-TCP backends this is environmental noise. If your e2e sees 1 flake in 3-5 samples, take more samples; if you see repeated flakes, that's a real bug — don't trust the implementer's "non-flake on 3 samples" claim without independent re-runs.

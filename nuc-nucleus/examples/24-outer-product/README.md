# Example 24 — Outer product (rank-1 / BLAS-2 `ger`)

The **outer product**: two 1D vectors produce a 2D matrix with **no
reduction**. Inputs are a length-M column vector `a` and a length-N row
vector `b`; output is the M×N matrix

```
c[i][j] = a[i] * b[j]
```

This is the conceptual **opposite of a reduction**: the rank EXPANDS
(1D × 1D → 2D) rather than contracting. Dims are **rectangular**
(M = 8, N = 16) on purpose, so `c` is non-square and the rank expansion
is unmistakable.

## What this example stresses

| Axis        | What                                                                |
| ----------- | ------------------------------------------------------------------- |
| Algorithmic | Rank-1 / outer product over TWO 1D inputs read with DIFFERENT index variables (`a[i]`, `b[j]`); a 2D row-major output written once per `(i, j)` with NO accumulate. |
| Scheduling  | Naive (host-only); the cross-backend differential workhorse.        |
| Backends    | Bit-identical against `reference.bin` for `naive` across all 7 tier-1 backends. |

This is a **distinct vertical** from the examples it superficially
resembles:

- **03-reduction / 23-dot-product** *contract* an axis (`sum_k …`). The
  outer product does the opposite — it introduces a new output axis for
  every input axis. It is the rank-EXPANSION counterpart of those
  reductions.
- **07-matmul** *contracts* along `k`: `c[i][j] = sum_k A[i][k]·B[k][j]`.
  The outer product is the degenerate "K = 1, no accumulate" rank-1
  building block that matmul sums over — there is no `k` loop and no
  accumulator here.
- **15-transpose** is a rank-preserving **permutation** of one input.
  The outer product reads two distinct 1D inputs and builds a 2D output
  from scratch.
- **01-elementwise-add** is a per-element **map** over two equal-length
  1D arrays with a **shared** index (`c[i] = a[i] + b[i]`). The outer
  product reads `a` and `b` with **different** index variables so the
  output is the full Cartesian M×N grid, not a single 1D result.

## The one new shape: two 1D reads with two distinct index vars

The kernel call is `mul(a[i], b[j])` — the outer loop variable `i`
indexes `a`, the inner loop variable `j` indexes `b`. This is a strict
**subset** of 07-matmul's mixed-index reads
`madd(c[i][j], a[i][k], b[k][j])` (which mixes `i`/`k` and `k`/`j` in 2D
index expressions *and* accumulates). Here each read uses exactly one
loop variable into a 1D array, and there is **no accumulate** — so it
introduces no new codegen surface and lowers on all 7 tier-1 backends.

Unlike 07-matmul, `c` is **not** pre-initialised to an accumulator
identity: each `c[i][j]` is a single straight assignment from one
product, not a fold.

## What this example does NOT stress

- **Reduction / accumulation.** There is no `sum_k`, no accumulator, no
  tree combine. That absence is the whole point — this is the rank
  EXPANSION counterpart to 03/23.
- **Float arithmetic.** PRD §10.1 invariant: bit-identity requires
  deterministic arithmetic. Integer only.
- **Distributed placement across compute workers.** The naive schedule
  places everything on `host`. A distributed variant would partition the
  `i` row axis (each worker owns a strip of rows of `c` and needs all of
  `b`), but that is out of scope; the naive cross-backend differential
  is the acceptance signal here.

## I/O format

Binary little-endian `i32` words. `M = 8`, `N = 16` (mirroring the
`const` declarations in `prog.algo.nuc`).

- **`input.bin`** ((M+N)·4 = 96 bytes): both vectors back to back.
  - bytes `[0 .. 4·M)`       — vector `a`: `M` LE `i32` words.
  - bytes `[4·M .. 4·(M+N))` — vector `b`: `N` LE `i32` words.
  This two-input single-file convention matches 01/23 (`load_a` reads
  `[0..M)`, `load_b` reads `[M..M+N)`).
- **`reference.bin`** (M·N·4 = 512 bytes): matrix `c`, row-major —
  `c[i][j]` at byte offset `(i·N + j)·4`.

Both fixtures are committed binaries, well under the 10 KB
inspectability cap (per
[`docs/reference-impl-policy.md`](../../../docs/reference-impl-policy.md)).

The input pattern is

```
a[i] = (i as i32) - 4      in [-4, 3]    (i in 0..8)
b[j] = (j as i32) - 8      in [-8, 7]    (j in 0..16)
```

Chosen because:

- Deterministic and reproducible (generated by the reference's
  `--gen-input`, no python step).
- Each product `a[i]·b[j]` is in `[-32, 32]` (|a| ≤ 4, |b| ≤ 8) — far
  inside the i32 range, so `wrapping_mul` never actually wraps on this
  fixture.
- The two offsets (−4, −8) make `a` and `b` straddle zero with different
  magnitudes, so the outer product has a non-trivial sign pattern (a
  transposed or dropped element changes the bytes), not an accidental
  all-zero or constant matrix.

## How to regenerate the fixtures

Per [policy §1](../../../docs/reference-impl-policy.md#1-file-layout),
the reference crate is both the generator and the witness:

```sh
# 1. write input.bin (96 bytes = a ++ b):
cargo run --release \
  --manifest-path nuc-nucleus/examples/24-outer-product/reference/Cargo.toml -- \
  --gen-input nuc-nucleus/examples/24-outer-product/input.bin

# 2. compute reference.bin (512 bytes = c, row-major):
cargo run --release \
  --manifest-path nuc-nucleus/examples/24-outer-product/reference/Cargo.toml -- \
  --in  nuc-nucleus/examples/24-outer-product/input.bin \
  --out nuc-nucleus/examples/24-outer-product/reference.bin
```

`just regen-references` auto-discovers this crate via glob and runs
step 2; step 1 (`--gen-input`) is the one-time bootstrap for `input.bin`.

## Reference implementation

`reference/` is a standalone Rust crate with no dependency on Nucleus,
on any backend crate, or on `kernels.rs` (policy §2, the independence
rule). It fills `c` row-major in a plain nested loop using the identical
`wrapping_mul`. No threads, no third-party crates, no `HashMap`.

## Numeric type choice & determinism: `i32`

PRD §10.1 invariant. Integer multiply is bit-deterministic. Crucially,
because there is **no reduction**, every output element `c[i][j]` is a
single independent product — the result is order-independent **by
construction**, with no associativity/commutativity argument needed
(there is nothing to reorder). That is why every tier-1 backend, under
any schedule, emits identical bytes. `wrapping_mul` documents the
overflow contract; the committed fixture stays inside the i32 range but
the choice is defensive.

## Contract-check limitation

Same scalar-only contract-pass limitation as examples 01 / 07 / 23.
Running `check_kernels_contract` against this example produces:

- **PASS** for `mul` — declared `(i32, i32) -> i32`, scalar in / scalar
  out, matches.
- **`TypeMismatch`** for `load_a` / `load_b` / `save_output` — declared
  aggregate (`i32[M]`, `i32[N]`, `i32[M][N]`); the scalar-only matcher
  emits the "aggregate type matching not yet implemented" diagnostic.
  Loud failure, not silent acceptance.

When aggregate matching lands (TASK-0103 / TASK-0012 follow-ups), this
example needs no change.

## Required schedules

- `naive.sched.nuc` — single worker (`host`), every kernel placed there.
  No loop transforms, no transfers. **Required** for tier-1 conformance
  on this example; the e2e gate verifies bit-identity against
  `reference.bin` across all 7 tier-1 backends.

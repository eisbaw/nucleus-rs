# Example 23 — Dot product (map-reduce / inner product)

The canonical **map-reduce**: elementwise-multiply two vectors, then
sum-reduce the products to a single scalar. Inputs are two length-N
vectors `a`, `b` (N=256 i32 LE words each), laid out as
`NUM_WORKERS x PARTITION_SIZE` (4 x 64). Output is a single i32 LE
scalar `result = sum_k a[k] * b[k]`.

## What this example stresses

| Axis        | What                                                                |
| ----------- | ------------------------------------------------------------------- |
| Algorithmic | Map-then-reduce composition over TWO inputs: a two-input elementwise map feeding a two-phase tree reduction. |
| Scheduling  | Naive (host-only); the cross-backend differential workhorse.        |
| Backends    | Bit-identical against `reference.bin` for `naive` across all 7 tier-1 backends. |

This is a **distinct vertical** from its two parents:

- **01-elementwise-add** is a pure **map** (`c[i] <-- add(a[i], b[i])`),
  no reduction.
- **03-reduction** is a pure **reduce** over a **single** input array,
  no map.
- **23-dot-product** is **map-then-reduce** over **two** inputs — the
  smallest standalone inner product. 07-matmul and 17-spmv compute
  dot-products internally, but there was no standalone one until now.

The map phase (`prod[w][i] <-- mul(a[w][i], b[w][i])`) is exactly 01's
two-input elementwise shape, now 2D-indexed. Phases 1 and 2 are
byte-for-byte the same two-phase reduction as 03-reduction (only the
source array differs — `prod` instead of `a`). No new codegen surface
is introduced; the example is pure composition.

## Why the explicit `prod` intermediate

The tier-1 backends' codegen rejects nested kernel calls inside an
argument expression (the IR represents them, but the shared
`render_fire_arg` helper every tier-1 backend uses rejects
`ArgBinding::Nested`), so the "fused" spelling
`accumulate(partials[w], mul(a[w][i], b[w][i]))` would not compile.
Materialising the map output into its own `data` symbol (`prod`) is the
convention throughout the examples (the same reasoning behind 03's
`half1`/`half2` scalar intermediates). It also keeps the map and reduce
phases visibly distinct and makes `prod` available as an inspectable
intermediate.

## What this example does NOT stress

- **Float dot products.** PRD §10.1 invariant: bit-identity requires
  deterministic arithmetic, and floating-point sum order is not
  reorder-invariant. Integer only.
- **Fused multiply-accumulate as a single kernel.** Kept as separate
  `mul` + `accumulate` so the reduce phases are literally 03's kernels
  and the map/reduce split stays visible.
- **Distributed placement across compute workers.** Like 03's naive
  schedule, everything is placed on `host`. Distributing the `w` axis
  is out of scope; the naive cross-backend differential is the
  acceptance signal here.

## I/O format

Binary little-endian `i32` words. `N = 256`, `NUM_WORKERS = 4`,
`PARTITION_SIZE = N / NUM_WORKERS = 64`. These mirror the `const`
declarations in `prog.algo.nuc`.

- **`input.bin`** (2048 bytes): both vectors back to back.
  - bytes `[0 .. 4*N)`   — vector `a`: `N` LE `i32` words, row-major
    over `i32[NUM_WORKERS][PARTITION_SIZE]`.
  - bytes `[4*N .. 8*N)` — vector `b`: `N` LE `i32` words, same layout.
  This two-input single-file convention matches 01-elementwise-add
  (`load_input` reads `[0..N)`, `load_input_b` reads `[N..2N)`).
- **`reference.bin`** (4 bytes): single LE `i32` word — the scalar
  `result`.

Both fixtures are committed binaries, well under the 10 KB
inspectability cap (per
[`docs/reference-impl-policy.md`](../../../docs/reference-impl-policy.md)).

The input pattern is

```
a[k] = (k % 7) - 3      in [-3, 3]
b[k] = (k % 5) - 2      in [-2, 2]
```

Chosen because:

- Deterministic and reproducible (generated by the reference's
  `--gen-input`, no python step).
- Each product is in `[-6, 6]` and the full N=256-term inner product is
  bounded by `256 * 6 = 1536` in absolute value — far inside the i32
  range, so the `wrapping_*` ops never actually wrap on this fixture.
- The two different small moduli (7 and 5) keep `a` and `b` out of
  phase, so the dot product is a non-trivial value (a dropped or
  swapped element changes `result`), not an accidental zero.

## How to regenerate the fixtures

Per [policy §1](../../../docs/reference-impl-policy.md#1-file-layout),
the reference crate is both the generator and the witness:

```sh
# 1. write input.bin (2048 bytes = a ++ b):
cargo run --release \
  --manifest-path nuc-nucleus/examples/23-dot-product/reference/Cargo.toml -- \
  --gen-input nuc-nucleus/examples/23-dot-product/input.bin

# 2. compute reference.bin (4 bytes = result):
cargo run --release \
  --manifest-path nuc-nucleus/examples/23-dot-product/reference/Cargo.toml -- \
  --in  nuc-nucleus/examples/23-dot-product/input.bin \
  --out nuc-nucleus/examples/23-dot-product/reference.bin
```

`just regen-references` auto-discovers this crate via glob and runs
step 2; step 1 (`--gen-input`) is the one-time bootstrap for `input.bin`.

## Reference implementation

`reference/` is a standalone Rust crate with no dependency on Nucleus,
on any backend crate, or on `kernels.rs` (policy §2, the independence
rule).

It computes the dot product a **deliberately different** way from the
Nucleus program: a single **flat left-to-right fold** over all N
products, rather than the partition-then-tree-combine shape the Nucleus
program uses. Because `wrapping_add` is associative **and** commutative
over i32, the flat fold and the partitioned tree reduction produce the
identical scalar — so a backend whose bytes match the reference is
unlikely to be "wrong in the same way". No threads, no third-party
crates, no `HashMap`.

## Numeric type choice & determinism: `i32`

PRD §10.1 invariant. Integer multiply and add are bit-deterministic
under any reordering — addition over i32 is associative *and*
commutative (two's-complement modular arithmetic forms a commutative
ring). That is precisely why the tree-combine pairing order is
irrelevant and every tier-1 backend emits identical bytes — the same
property 03-reduction relies on. `wrapping_mul` / `wrapping_add`
document the overflow contract; the committed fixture stays inside the
i32 range but the choice is defensive.

## Contract-check limitation

Same scalar-only contract-pass limitation as examples 01 / 02 / 03.
Running `check_kernels_contract` against this example produces:

- **PASS** for `mul`, `accumulate`, `combine` — all declared
  `(i32, i32) -> i32`, match.
- **PASS** for `save_output` — declared `(i32) -> ()`, scalar in /
  unit out, matches.
- **`TypeMismatch`** for `load_input` / `load_input_b` — declared
  `() -> i32[NUM_WORKERS][PARTITION_SIZE]`, aggregate-typed; the
  scalar-only matcher emits the "aggregate type matching not yet
  implemented" diagnostic. Loud failure, not silent acceptance.

When aggregate matching lands (TASK-0103 / TASK-0012 follow-ups), this
example needs no change.

## Required schedules

- `naive.sched.nuc` — single worker (`host`), every kernel placed
  there. No loop transforms, no transfers. **Required** for tier-1
  conformance on this example; the e2e gate verifies bit-identity
  against `reference.bin` across all 7 tier-1 backends.
